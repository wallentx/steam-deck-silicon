# LCD Deck ISP 3.0.0 and the shipped Mero driver

**CONFIRMED.** Magic Leap shipped an x86 Linux driver for ISP 3.0. Its AMDGPU module registers `isp_v3_0_ip_block`, passes graphics-memory, clock and power callbacks to its kernel camera driver, and contains a Mero-specific firmware request. Valve’s kernel package matching the captured Deck build takes a different branch. It skips ISP 3.0.0 during AMDGPU registration. **UNKNOWN.** The Deck’s ability to run this firmware or process even one frame. The Deck was off during this follow-up. The observations below combine its saved capture with newly examined distributor binaries. [Deck boot](../evidence/deck-live/subsystems.txt) · [Valve kernel package](https://steamdeck-packages.steamos.cloud/archlinux-mirror/jupiter-3.9/os/x86_64/linux-neptune-72-7.2.7.valve2-2-x86_64.pkg.tar.zst) · [Magic Leap build 9601 provenance](../evidence/artifacts.md)

## What the two inventories describe

Both BIOS files contain the same 16-byte ISP record, `2c 00 00 02 03 00 00 00 00 80 01 00 00 b0 40 02`. In the v2 IP discovery format this means hardware ID 44, instance 0, two little-endian base descriptors, version 3.0.0 and zero in the per-instance harvest field. The records immediately before and after it in on-disk order are HDP 5.0.4 (ID 41) and MMHUB 2.3.0 (ID 34) on both systems. Their adjacency describes table order. [AMD discovery layout](https://github.com/torvalds/linux/blob/8d3ae59288f1e7d58d76558a6ee96d533bc5019f/drivers/gpu/drm/amd/include/discovery.h#L88-L121) · [AMD hardware IDs](https://github.com/torvalds/linux/blob/8d3ae59288f1e7d58d76558a6ee96d533bc5019f/drivers/gpu/drm/amd/include/soc15_hw_ip.h#L60)

**CONFIRMED.** Both base values, `0x00018000` and `0x0240b000`, also match AMD’s named Van Gogh `ISP_BASE__INST0_SEG0` and `SEG1`. AMDGPU handles discovery register bases in dwords. The entries contain no extent, CPU physical address, access permission, interrupt routing or readiness bit. There is a narrower software cross-check for segment 0. The shipped Mero kernel’s `isp_get_cmd_buf_regs` contains the byte offset `0x6102c`, numerically `0x18000 × 4 + 0x102c`. Segment length, the role of segment 1 on Jupiter and usable register ranges on this Deck remain **UNKNOWN**. [AMD Van Gogh segment definitions](https://github.com/torvalds/linux/blob/8d3ae59288f1e7d58d76558a6ee96d533bc5019f/drivers/gpu/drm/amd/include/vangogh_ip_offset.h#L786-L791) · [AMDGPU unit and conversion](https://github.com/torvalds/linux/blob/8d3ae59288f1e7d58d76558a6ee96d533bc5019f/drivers/gpu/drm/amd/amdgpu/amdgpu_discovery.c#L1627-L1660)

## Where Jupiter stops

1. **CONFIRMED in Linux v7.2.** `amdgpu_discovery_reg_base_init` reads the validated table and populates `reg_offset` and `ip_versions` for internal `ISP_HWIP`. `amdgpu_discovery_sysfs_ips` creates kobjects from the cached records, including `base_addr`. The sysfs harvest formatter’s switch has no ISP case and starts at zero. This explains how a named ISP and `harvest=0` can appear without any ISP initialization. [Parser and version assignment](https://github.com/torvalds/linux/blob/8d3ae59288f1e7d58d76558a6ee96d533bc5019f/drivers/gpu/drm/amd/amdgpu/amdgpu_discovery.c#L1498-L1692) · [Export and harvest formatter](https://github.com/torvalds/linux/blob/8d3ae59288f1e7d58d76558a6ee96d533bc5019f/drivers/gpu/drm/amd/amdgpu/amdgpu_discovery.c#L1148-L1274)
2. **CONFIRMED in the matching Valve build.** In `amdgpu_discovery_set_ip_blocks`, `.text+0x6eb52` compares the masked version with `0x04010000`, then `+0x6eb5d` compares with `0x04010100`. The corresponding relocations at `+0x6ec0d` and `+0x6eb67` select `isp_v4_1_0_ip_block` and `isp_v4_1_1_ip_block`. A 3.0.0 value takes the successful exit at `+0x6eb73` without adding an ISP. The `amdgpu_discovery.c` file at the matching Neptune commit `31504582a07316ae0e8a8fb3b8fdc39d94842816` and the upstream v7.2 file have the same SHA-256, `2a53ce988fe75f16a00bd010c5c199449596936d7869223e65fc39917ae52be8`. The upstream ISP `early_init` also rejects unknown versions if called. On the Deck’s normal path it is never called for 3.0.0. [Valve package](https://steamdeck-packages.steamos.cloud/archlinux-mirror/jupiter-3.9/os/x86_64/linux-neptune-72-7.2.7.valve2-2-x86_64.pkg.tar.zst) · [Neptune commit and selector](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/amdgpu/amdgpu_discovery.c#L2823-L2839) · [Early init](https://github.com/torvalds/linux/blob/8d3ae59288f1e7d58d76558a6ee96d533bc5019f/drivers/gpu/drm/amd/amdgpu/amdgpu_isp.c#L101-L126)
3. **CONFIRMED in the saved boot.** The observed ten AMDGPU blocks omit ISP. `CONFIG_DRM_AMD_ISP=y` and `CONFIG_VIDEO_AMD_ISP4_CAPTURE` is unset. Enabling the capture option alone would leave the 3.0.0 registration gate in place. The binary examined here comes from Valve’s package for `7.2.7-valve2-2-neptune-72-g31504582a073`. Its SHA-256 is `74e91706bf8191ca2319df7d3fb3996f9b6350234ddb56b011a88d1b50d7d14b`, the decompressed `amdgpu.ko` SHA-256 is `990f7525b2325a617ecdf8e3cde2669d011c35b4e8735a6732a1902664855a02`, and its ELF build ID is `65662cc623f2f9609bd466ba54f497a5aba4a5b1`. A byte-for-byte hash of the installed module was unavailable in the saved capture. ## Can it process a frame from memory?

**STRONG EVIDENCE for a Mero internal memory-input mode.** The kernel function `isp_is_mem_camera` at linked VA `0xffffffff81a81140` returns true for camera ID 3. `isp_get_cmd_buf_regs`, `isp_init_fw_ring_buf` and `isp_send_fw_cmd_by_dma_buf` identify the command path. The `mero_isp.bin` image independently identifies an ISP 3.0 read-DMA implementation at `0xa95c`, write DMA at `0xabc8`, MIPI at `0xb058`, and a YUV422 loopback that skips the core pipeline at `0x18abc` and `0x1cfc8`. The second RAM image carries corresponding read/write DMA and MIPI paths at `0x26a64`, `0x26a94` and `0x26be8`. A mode-4 diagnostic at `0x14740` in the AMDGPU image explicitly limits full YUV capture. This leaves the formats and transformations of an independently supplied memory buffer unresolved. The separate `m2m` names in calibration routines would be ambiguous in isolation. [Vendor artifact hashes](../evidence/host-index.tsv)

**CONFIRMED public-facing limitation in the shipped configuration.** `vendor/etc/camera_capability_0.xml` line 984 and `_1.xml` line 1126 each declare zero Android input streams. They advertise RAW capability and `YCbCr_420_888` output, among other output formats. The 64-bit `camera.raven.so` contains references to both XML paths at file offsets `0x30d09` and `0x35270` and to `/dev/video0` at `0x35c88`. The HAL also contains `amdCamera3Reprocess` symbols. This documents a distinction between internal reprocessing facilities and the two advertised camera configurations. **UNKNOWN** whether any supported interface accepts an arbitrary sensorless frame on ML2 or Jupiter. No image was submitted to either device. [Camera configuration and HAL hashes](../evidence/host-index.tsv)

## Validation and driver requirements

**Smallest read-only Deck check, when it is next running.** Read the cached per-instance attributes on the GPU BDF from the saved boot. The expected result is two bases, `0x00018000` and `0x0240B000`. The basis for the expected result is the matching BIOS IPDS region. This records the values under the live sysfs names and entails no MMIO. A completed boot log can separately establish whether the running build added an ISP. [Cached sysfs formatter](https://github.com/torvalds/linux/blob/8d3ae59288f1e7d58d76558a6ee96d533bc5019f/drivers/gpu/drm/amd/amdgpu/amdgpu_discovery.c#L965-L997)

```sh
isp=/sys/bus/pci/devices/0000:04:00.0/ip_discovery/die/0/44/0
cat "$isp/num_base_addresses" "$isp/base_addr"
```

**Highest-value offline step.** Magic Leap’s 2024 notice offers the corresponding Linux 5.4.19 source (line 1688182). Its as-of-May-2022 file list, lines 1689970–1690090, explicitly names `drivers/media/platform/amd-isp3` sensor drivers, `isp_gfx_if.h`, `cmdresp.h`, `chip_offset_byte.h`, `chip_offset_ix2mm.h`, `isp_mc_addr_mgr.c`, `isp_pwr.c` and `phy.c`. This provides a specific source request for the x86 build 9601, BSP R64, including camera configuration and AMDGPU glue. The public file list identifies which source files would settle the register and ABI questions. An exact-build public source checkout for that subtree was unavailable in this investigation. [Magic Leap’s source offer and file list](https://site-assets.magicleap.com/live/dotCOM/ML2HW_Consolidated_notices_11_26_2024.txt) · [Earlier source inventory](../evidence/source-references.md)

**POSSIBLE port, conditional on that evidence.** A minimal driver would need validated register spans and interrupt mapping, a compatible firmware load path, power/reset ownership, a description of command and response rings, buffer addressing and lifetime, and a board-independent input mode or a routed sensor with calibration. The ISP4 code builds different versioned resources and interrupts. The Mero binary supplies leads for an ISP3 implementation, including a way to audit each CVIP dependency. **UNKNOWN** whether a useful workload can ever run on this LCD Deck. The next experiment is an offline source and ABI comparison. [Upstream ISP4 platform resources](https://github.com/torvalds/linux/blob/8d3ae59288f1e7d58d76558a6ee96d533bc5019f/drivers/gpu/drm/amd/amdgpu/isp_v4_1_1.c#L279-L320)

### Separate proposal requiring approval

On an expendable, vendor-supported Mero system, a single known input frame could test the internal memory path once source review identifies a supported submission interface, its format and buffer bounds. A successful completion and matching output dimensions, format and expected pixel transform would establish that specific path on Mero. A timeout or rejected input would identify the first failing stage only if the stock driver exposes that status. Risks include disrupting the camera service or hanging the device on a DMA or firmware error. Stop the test and recover through the existing stock boot if necessary. This proposal requires explicit approval and has not been run.

## Reproducing the binary comparisons offline

Use the two distinct AMDGPU files extracted from the linked Valve package and ML2 vendor partition. Give them local names `valve-amdgpu.ko` (decompressed with `zstd`) and `ml-amdgpu.ko`. All commands below operate on regular files. The module output uses ELF section-relative addresses. In the decompressed ML2 kernel ELF, the kallsyms count of `55,397` is at file offset `0x17a18c0`, names start at `0x17a18c8`, and the token table starts at `0x184b340`. The `__ksymtab` entry at `0x19e7bd8` independently resolves `isp_init`. The ROM output should show the same 16 bytes in both images. [ML2 extraction guide](../reports/reproduction.md) · [Valve BIOS package and hashes](steam-deck-applicability.md)

```sh
od -An -tx1 -j $((0x234918)) -N 16 F7A0133_sign.fd
od -An -tx1 -j $((0x14c9b8)) -N 16 demophon_bios.FD
llvm-objdump -dr --disassemble-symbols=amdgpu_discovery_set_ip_blocks valve-amdgpu.ko | rg -B 8 -A 3 'isp_v4_1_[01]_ip_block'
llvm-objdump -dr --disassemble-symbols=nv_set_ip_blocks,isp_sw_init ml-amdgpu.ko | rg 'isp_v3_0_ip_block|isp_init-|cvip_set_gpuva|request_firmware'
strings -tx mero_isp.bin | rg 'ISP_3_0/IspHw(RDma|CoreWDma|Mipi)\.c|YUV422 post loopback'
```
