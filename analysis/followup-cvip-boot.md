# What the LCD BIOS does with the CVIP power label

**CONFIRMED in the F7A0133 executable.** Valve's `SmuV13Dxe` selects between two feature-control defaults using CPUID. Both clear the bit it prints as `FEATURE_CVIP_DSP_DPM`. The diagnostic obtains that bit from a UEFI Platform Configuration Database (PCD) token. It does not read a CVIP fuse or measure a rail. Dynamic power management (DPM) describes clock/power policy. Its configuration cannot establish whether the DSP exists, is powered, or can be booted. The saved Deck capture contains no trace of this routine running. [Capsule and module hashes](steam-deck-applicability.md) · [AMD's Van Gogh SMU feature definitions](https://github.com/torvalds/linux/blob/8d3ae59288f1e7d58d76558a6ee96d533bc5019f/drivers/gpu/drm/amd/pm/swsmu/inc/pmfw_if/smu_v11_5_pmfw.h#L83-L89)

## Follow the value through the executable

Offsets below are zero-based RVAs in the extracted x86-64 `SmuV13Dxe` PE, SHA-256 `371b04c3cc217922828d32889512a342eb4c85a516dcd5b590ca72039685ad61`. The prior comparison found the same PE hash in F7A0131 and F7A0133. The follow-up independently extracted it from F7A0133. [Valve's package](https://steamdeck-packages.steamos.cloud/archlinux-mirror/jupiter-main/os/x86_64/jupiter-hw-support-20261028.1-2-any.pkg.tar.zst)

| Static call chain | What the instructions establish |
|---|---|
| `0x100b → 0x1da8` | The caller invokes the routine named by the `SmuFixupPlatformConfigFF3` diagnostic. It requests CPUID leaf `0x80000001` at `0x1dde`. The helper executes CPUID at `0x305` and returns EAX through a pointer. At `0x1df9–0x1e31` the predicate checks base family 0xf, extended family 8, extended model 9 and base model below 8. It labels the matching arm VN and the fallback MR. These are firmware branch labels. |
| VN `0x1e78 → 0x1e9e`, MR `0x1f0f → 0x1f35` | The VN arm supplies `0x0743693b` and the MR arm `0x04000020` to token `0x41200`. Firmware calls this `PcdSmuFeatureControlDefinesExt`. Bits 19, 20 and 21 are clear in both constants. The wrapper at `0x4910` supplies token-space GUID `7788adf0-9788-4a3f-83fa-cb512e7cf8dd` and calls protocol slot `+0x50` (`Set32`). Other code also writes this PCD, including a conditional bit-7 adjustment at `0x1091–0x10b2`. A branch default alone cannot supply the final boot value. |
| `0x1285 → 0x48e4`, `0x129e → 0x2f50` | The extended-word getter obtains the interface using the PI PCD protocol GUID at `0x7b80` (`13a3f0f6-264a-3ef0-f2e0-dec512342f34`) and dispatches through `+0x18` (`Get32`). Its result reaches EDX at the diagnostic call. ESI retains that second argument at `0x2f6c`. The PI protocol definition fixes both method offsets on x86-64. [EDK II GUID and ABI](https://github.com/tianocore/edk2/blob/0f3867fa6ef0553e26c42f7d71ff6bdb98429742/MdePkg/Include/Protocol/PiPcd.h#L397-L416) |
| `0x358c / 0x35ab / 0x35c7` | Consecutive tests select the ISP, A55 and CVIP DSP DPM text. At `0x35d0` the last test masks `0x00200000`. At `0x35dd` it selects the enable/disable string and at `0x35e1` calls the shared formatter. Bit 21 of the extended word corresponds to feature 53, matching AMD's published interface. No CVIP power-up call occurs in this diagnostic sequence. [Linux Van Gogh feature and message mappings](https://github.com/torvalds/linux/blob/8d3ae59288f1e7d58d76558a6ee96d533bc5019f/drivers/gpu/drm/amd/pm/swsmu/smu11/vangogh_ppt.c#L116-L121) |

An independent structure check locates the same token in the capsule. Starting at F7A0133 file offset `0x3fcc70`, the GUID-defined section's LZMA stream begins at volume offset `0xa8`. In its expanded bytes the version-7 PCD database begins at `0xa22d4`. SHA-256 of its declared 55,128 bytes is `1306269b5773576e571b93cd998c2390a83553dccc02d69375d2fb8d60f62f09`. The dynamic-ex row at database offset `0x658` maps token `0x41200` to local number 168 and GUID index 3. Table entry `+0x579c` is `0x0400d89c`, a UINT32 in the zero-initialized tail. The initialized region ends at `0xd758` and the tail is 935 bytes long. Reading bytes beyond the on-disk database as the token value would read unrelated data. The executable's explicit assignments above are stronger evidence of policy. [EDK II database layout](https://github.com/tianocore/edk2/blob/0f3867fa6ef0553e26c42f7d71ff6bdb98429742/MdeModulePkg/Include/Guid/PcdDataBaseSignatureGuid.h#L55-L135)

## From policy to a booted endpoint

| Evidence | LCD Deck compared with Magic Leap 2 |
|---|---|
| Power and rail configuration | Deck setup contains the reserved-memory test and VDDCR_CVIP TDC/EDC fields. The DXE also formats rail limits. In the matching ML2 1.12.1 module (SHA-256 `7f7b5ddaf71385055fa9523400b964036b652d0072b7bd3fb53f099e1f151cfe`), the literal `CVIP` occurs zero times in ASCII or UTF-16LE, case-insensitive. Neither Deck branch constant occurs as a little-endian word in that PE. A platform with a documented CVIP can ship a differently instrumented SMU driver. A string count is a poor board-presence test. [ML2 module provenance](../evidence/revision-bios.md) |
| Memory and firmware handoff | The Deck ABL's type-0x11 memory-category string has no associated live base/length in the capture. In all four ML2 releases, ABL subtypes 0x05/0x14 carry the partition lookup, destination and NVMe copy diagnostics. The Deck F7A0131/0133 expanded ABL subsections lack those specific diagnostics. The inspected level-two PSP directories on both platforms omit type 0x57. That absence is **DISPROVEN as a discriminator** in this comparison. [Subtypes, exact offsets and hashes](../evidence/revision-bios.md) |
| Reset and bridge | AMD's published PSP history records a BL-to-trusted-OS carveout, a CVIP power-on handler and reset release. Its AGESA history attributes enabling CVIP PCIe bridge hotplug to Mero. These are development records across products. They provide no Jupiter execution log. The Deck's captured GP18 has a dummy function and no function 1. The four ML2 BIOSes describe that child and the four x86 kernels match `1022:149d`. These are static ML2 records. [PSP history](https://chromium.googlesource.com/chromiumos/third_party/coreboot/amd_blobs/+/8d9190d5a70c46dda257fa71210a77f0559ee56a/cezanne/PSP/PSP_ReleaseNotes.txt#1252) · [Mero bridge change](https://chromium.googlesource.com/chromiumos/third_party/coreboot/amd_blobs/+/8d9190d5a70c46dda257fa71210a77f0559ee56a/cezanne/PSP/AgesaBLReleaseNotes.txt#1779) · [Deck live ACPI](../evidence/deck-live/acpi.md) |

**UNKNOWN on Jupiter.** No saved firmware trace shows the selected default, a CVIP allocation handed to the PSP, an acknowledged power transition, reset release or a running CVIP image. A board-matched existing boot trace with any such handoff would narrow the initialization question. Exact-mask physical documentation and board rail/routing or fuse provenance would be needed to distinguish physically omitted hardware from permanent disablement. Reading a DPM configuration bit alone cannot settle either question.

The PE disassembly above can be repeated offline with `llvm-objdump -d --start-address=0x1da8 --stop-address=0x1f67 SmuV13Dxe.efi` and the same command over RVAs `0x2f50–0x35e6`. The [existing extraction notes](steam-deck-applicability.md) identify the package, GUID and section. No firmware component was executed.
