# ISP3 response interrupts and the two Jupiter register segments

**CONFIRMED on Mero's software path.** The ISP receives interrupts through AMDGPU's interrupt handler (IH). Its response worker can also check for work after a timed wait. A frame callback therefore identifies the result of the response path; by itself it cannot establish that a particular interrupt fired. **UNKNOWN on Jupiter.** The matching kernel can dispatch this class of interrupt, but the recorded Deck boot registers no ISP3 source. [Jupiter boot inventory](../evidence/deck-live/isp3-boot-check.md)

## From interrupt vector to consumer

The Mero references use build 9601. `K:` is the x86 kernel VA relative to `0xffffffff81000000`, SHA-256 `f8891033b1f3b9cf9f25ef76d914173f1d43ff9a75df6764982207f0bd84f642`. Module numbers are `.text` offsets in `amdgpu.ko`, SHA-256 `ca31bf6b6751b6bcf8073daf7244a3dfb437e938c40905a5d5f04b94bc86cb9f`. [Member paths](../evidence/host-index.tsv)

| Stage | Direct evidence |
|---|---|
| Register | `isp_register_isr` passes client **5** and callback addresses at `K:a77e8e–a77ea8`. The four little-endian source IDs at kernel **file** offset `0x1cd6c00` are **4, 6, 8, 10**. The graphics-services adapter calls `amdgpu_irq_add_id` and `amdgpu_irq_get` (module relocations `+0x15873e/+0x158796`). The separate ISP set-state callback at `K:a77e40` returns zero. Successful software registration is weaker evidence than a delivered interrupt. |
| Route | Module `cgs_process_irq` recovers the camera callback, registered source and vector data at `+0x158829–0x158847`. `isp_isr` validates the source via the `0x55` bitmap at `K:a77d51–a77d62`. For accepted sources the indexed table at kernel file `+0x17037d0` selects workers **0, 1, 2, 3** respectively. The ISR signals that worker's event at `K:a77dc4`. These are GPU source IDs, separate from the ML2 CVIP PCI/MSI-X transport. |
| Drain | `isp_fw_resp_thread_wrapper` passes 5 to `isp_event_wait` at `K:a77b1f–a77b24`, checks the stop flag, locks, and calls `isp_fw_resp_func` at `K:a77b65`. The return from the event wait does not decide whether to drain. `isp_get_f2h_resp` checks the slot checksum. Command acknowledgement and frame completion are different messages. [Response fields and ownership](isp3-command-protocol.md#response-fields-and-lifetimes) |
| Return and release | `RESP_ID_FRAME_DONE` dispatches at `K:a84ac9`. The handler checks the metadata reference, then invokes callback event `0x10` at `K:a84409`. The camera callback reaches `vb2_buffer_done` at `K:a45af4`. Teardown includes the `isp_unregister_isr` path through the release callback at `K:a78110` and stopping the response workers. A wakeup or a command acknowledgement alone supplies no completed pixel buffer. [Frame return path](isp3-frame-evidence.md) |

**CONFIRMED infrastructure, UNKNOWN electrical route.** In Neptune commit `31504582a07316ae0e8a8fb3b8fdc39d94842816`, the Navi10 IH uses the generic vector decoder. Its first dword carries the client in the low eight bits and the source in the next eight. The dispatcher recognizes ISP client 5. It directs an already mapped source to a Linux virtual IRQ or looks it up in the client's registered sources. Stock Jupiter registered Navi10 IH, but skipped the ISP3 block. No saved vector from Jupiter ties sources 4/6/8/10 to an ISP event. **DISPROVEN** that Neptune's ISP4 response-source list can be copied unchanged. ISP4.1.1 selects eight write-pointer interrupts with odd IDs 1 through 15. Its header assigns even IDs 4, 6, 8 and 10 to *base changes* for rings 11–14. Mero's observed four-ID response-worker mapping differs. ## Register accessibility

| Cached Jupiter descriptor | Byte offset | What Neptune source establishes |
|---|---:|---|
| Segment 0, `0x00018000` dwords | `0x00060000` | Inside the observed 512 KiB register BAR5. In the ordinary bare-metal path, an in-range dword offset qualifies for direct aperture access. |
| Segment 1, `0x0240b000` dwords | `0x0902c000` | Outside BAR5. For such an offset passed to the generic dword reader, Neptune delegates to `amdgpu_reg_pcie_rd32`, which in turn requires a backend callback. This is evidence of an indirect access mechanism in the driver. It does not identify a second assigned ISP BAR, segment extent, permission or responsive hardware. |

The Mero CGS normal register operation resolves to `amdgpu_mm_rreg` at module relocation `+0x1572d1`. On Jupiter the discovery bases match AMD's named Van Gogh segment macros. The actual block clock/reset, board prerequisites, source-to-IH wiring and register responses remain **UNKNOWN**. No register transaction was performed.
