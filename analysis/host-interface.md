# Host transport and shared memory

The x86 image contains two related communication paths. The PCI probe establishes resources and registers a Linux mailbox controller. The Mero XPC driver separately exposes command, queue and notification operations and calls the PL320 routines directly. A third layer, MLNET, provides a network interface over which the host makes filesystem services available. The x86 built-in driver manifest independently identifies cvip, cvip_s_intf, mero_xpc, gsm, shregion, mlnet and mero_notifier. The graph across these components establishes a system interface for vendor services. The public application interface for arbitrary neural networks remains UNKNOWN. ## Interfaces still missing

The full XPC command namespace, version negotiation, coherent-buffer contract, per-task descriptors, error recovery, and ownership transitions across host sleep require matching source or a known-good trace. The interrupt handler and command symbols establish mailbox signaling. A separate, generic GPU-style compute doorbell ABI remains UNKNOWN. Generic Android NNAPI, Linux remoteproc and rpmsg interfaces have no demonstrated role in this path.

A Linux driver would need an enumerated, firmware-initialized endpoint and valid resources before any binding work. Porting the ML2 path would also require a compatible mailbox controller and IRQ routing, IOMMU and shared-memory lifecycle, readiness negotiation, and eventually a matching task loader and licensed DSP toolchain. An x86 userspace runtime alone cannot create the absent PCI function. [Vendor source availability](../evidence/source-references.md)
