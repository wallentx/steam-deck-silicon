# ISP3 buffer addresses, geometry and ownership on Jupiter

**CONFIRMED in the Mero host code.** The normal image-output path can hand the ISP an AMDGPU buffer object's memory-controller (MC) address after a GTT pin and GART allocation. The source of that address can be traced through the creation and lookup of the same object. Command and response rings also have separately tracked CPU and MC bases. **UNKNOWN on Jupiter.** No captured memory-camera submission supplies an input plane and identifies the address space that its read-DMA engine actually uses. An ordinary output descriptor and a named firmware input handler do not settle that question.

The binaries are the ML2 build-9601 `vmlinux` (`f8891033b1f3b9cf9f25ef76d914173f1d43ff9a75df6764982207f0bd84f642`), `amdgpu.ko` (`ca31bf6b6751b6bcf8073daf7244a3dfb437e938c40905a5d5f04b94bc86cb9f`) and the 64-bit camera HAL (`907dd72aea4798cd6c5d115653abb246ac06b452c35c0d91d31960e7fd402eb2`). Below, **K** prefixes the low 24 bits of a linked x86 kernel address based at `0xffffffff81000000`, **M** is the module's ELF `.text` offset, and **H** is a camera HAL ELF virtual address. For example, K:a3adb0 means `0xffffffff81a3adb0`. All observations are static or come from the linked, previously collected inventories. [Artifact index](../evidence/host-index.tsv) · [Original address-path audit](isp3-buffer-dependencies.md)

## Ordinary output

**Where the MC value originates.** In Mero’s `amdgpu_gem_object_create`, the relevant success path pins the object in domain 2 (GTT) at M:20313, calls `amdgpu_ttm_alloc_gart` at M:2034f, obtains its kernel mapping at M:2036f and calls `amdgpu_bo_gpu_offset` at M:203fa. The store at M:20403 records that result. The GEM object is embedded at BO+0x50. After a successful GEM handle lookup and flag check, `amdgpu_gem_gartmc_ioctl` reads GEM+0x360 at M:21080, the same BO+0x3b0 location, and returns the 64-bit value. No CPU physical address conversion is needed to explain the output value. The separate kernel VA, a dma-buf file descriptor and the application's GPUVM VA each have different lifetimes and meanings. [HAL, GBM, Mesa, libdrm and GEM consumers](isp3-buffer-dependencies.md#where-android-gets-the-frame-address)

**What one plane carries.** `getBufDetails` reads the allocator's pitch from the native handle at H:8d73a. `map_img_addr` copies the format, width, height and two vendor stride values at K:a3ae1b–a3ae3e. The debug text referenced at K:a3b012 identifies the geometry and both strides. The host represents each plane's MC address with two 32-bit halves and its byte extent with a 32-bit value. Adjacent chroma planes are derived from the base and preceding extents. This identifies the width of the **carrier**. The number of translated or electrically decoded ISP address bits remains **UNKNOWN**.

| Normal output format | What build 9601 does | Proof boundary |
|---|---|---|
| NV12 / NV21 | The format table at kernel ELF file offset `0x1cce880` names the two-plane layouts and internal codes 1/2. The common branch at K:a3af01–a3af24 describes the luma extent as height × Y stride and the interleaved chroma extent as height × the vendor UV stride. The HAL's 4:2:0 branch at H:8d75d sets that UV field to half the allocator pitch. | For an even 640 × 480 image with a 640-byte Y pitch, those extents are 307,200 and 153,600 bytes. This is a worked output-layout check. The HAL allocation-length calculation uses rounded-up half height. Treat its stride convention as specific to this interface. |
| I420 / YV12 | Internal codes 3/4 correspond to three named planes. The host computes the two chroma extents with an additional division by two (K:a3ae98–a3aec0, K:a3af41–a3af81) and reverses their storage order for YV12. | The byte order of the two chroma planes matters even when their extents match. These are linear host layout formulas. A modifier-specific/tiled layout or raw **input** needs its own contract. |
| Raw | The output table names RAW8/10/12/14/16, with different firmware codes. At K:a3aec5–a3aee2 the raw branch uses the supplied total length for codes 11–13 and 15. Code 14 (RAW14) is in the table but reaches the unsupported-format path in this helper. | Neither a table entry nor a total byte count proves sensorless input packing, valid stride, or a particular transformation. |

The host sets the low descriptor control words to 0 and 4 before writing the plane addresses (K:a3ae58–a3ae71). **STRONG EVIDENCE** for a GPU-address, context-zero interpretation on this output path. AMD’s published **different-generation** ISP header places a tag before a packed space/VMID word, defines space 4 as GPU VA, and then lists low/high address and size triples. That layout agrees with the observed stores and the BO producer. It does not establish that all Mero commands share the later ABI, or that Jupiter's read-DMA engine shares the output writer's context. [AMD comparison header](https://github.com/amd/Linux_ISP_Kernel/blob/5b316a3d3ba4f799cb333c823b87f0793ea139a2/drivers/media/platform/amd/isp4/isp_module/src/isp_fw_if/param_types_pub.h#L714-L755) · [Stock frame control and memory-input gap](isp3-frame-evidence.md)

## Rings and pixel buffers have different contracts

| Resource | Allocation and ownership | Synchronization and limit |
|---|---|---|
| Firmware work arena | **CONFIRMED.** `isp_init` passes selector `0x446e6942` at K:a91aea. Its `ispm_sw_init` arm requests **100 MiB** (`0x6400000`) via `lfb_resv_imp` at K:a786b8–a786bd. The cold branch calls `isp_gpu_mem_alloc` at K:a9eaa4. That allocator passes 32 KiB alignment and a 256 MiB maximum **heap offset**. Separate CPU and MC mapping outputs reach `isp_fw_work_buf_init` at K:a78786–a7878e. | A separately compiled helper, `isp_fw_work_mem_rsv`, requests **11 MiB** with the same alignment and a 4 GiB heap-offset argument at K:a84c61–a84c7e. The 11 MiB work layout and the normal 100 MiB backing request are distinct. Neither number sets the image plane's alignment or the device DMA mask. |
| Command, response and payload subregions | The accessors add the same bounded, ring-specific displacement to each of the CPU and MC bases. Four `0x1900`-byte command rings start at arena offset `0xa00000`. Four `0x3200`-byte response rings start at `0xa06400`. The payload area is `0xed400` bytes at `0xa12c00`, ending at `0xb00000` (K:a921f0, K:a92290, K:a92330). The payload allocator rounds slot addresses up to 64 bytes (K:a924d9–a924e4). | The host fences its command record copy before publishing the write pointer (K:a87911) and fences after publishing the response read pointer (K:a8a1b5). These order the observed ring operations. They do not flush an input image, establish a cross-device fence, or prove pixel-buffer coherence. [Command and response traces](isp3-command-protocol.md) |

The frame callback hands VB2 a completed buffer in state 5 at K:a45aef–a45af4. Queue stop also hands back active buffers, in state 6 at K:a44e36–a44e3b. ## Does Jupiter advertise an independent ISP requester?

**CONFIRMED for a public Jupiter capture.** The Linux Hardware Database's `F3B9E861E0CA.bin` includes a checksum-valid 420-byte ACPI IVRS table, revision 2, SHA-256 `62fb4dc6d954e6988202fe0444174ce70c9991b21e89d2b647b0958d310494ef`. The IVHD blocks at offsets `0x30`, `0x78` and `0xd0` are types `0x10`, `0x11` and `0x40`, with segment 0 and IOMMU device ID 2. All describe a broad requester-ID range `0x0008…0xfffe`. The four explicitly named ACPI-HID entries in the type-0x40 block name `AMDI0020` and UARTs `FUR0` through `FUR3`. None names an ISP. The other public Jupiter table dump, `D98C04F8D964.bin`, has 30 table headers and no IVRS. The owner's archived DSDT/SSDT set and this public IVRS are separate captures. [Public IVRS bytes](https://github.com/linuxhw/ACPI/blob/d6d30c6ef6f45506567f25a302c64f009d8f5f4e/Notebook/Valve/Jupiter/Jupiter/F3B9E861E0CA.bin#L3448-L3475) · [Other Jupiter capture](https://github.com/linuxhw/ACPI/blob/d6d30c6ef6f45506567f25a302c64f009d8f5f4e/Notebook/Valve/Jupiter/Jupiter/D98C04F8D964.bin) · [Neptune IVHD parser](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/iommu/amd/init.c#L1470-L1653)

The owner’s PCI inventory identifies AMDGPU at `04:00.0` and the ISP in that GPU's discovery table. No separately attributed ISP PCI or media device appears. A broad IVRS range can cover an unnamed requester, and an integrated DMA master could share a parent identity. Neptune's Van Gogh MMHUB 2.3 fault-decoding name list contains no ISP label. That partial string table cannot identify the ISP's actual fabric client or disprove a shared path. **UNKNOWN** on Jupiter: the ISP's hardware requester ID, whether an independent system-IOMMU domain can be selected, which hub/context each engine uses, and whether image read DMA can reach the same pages as the output writer. [Boot inventory](../evidence/deck-live/isp3-boot-check.md) · [MMHUB 2.3 names](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/amdgpu/mmhub_v2_3.c#L34-L56)

## What the matching Neptune kernel can supply

At Neptune commit `31504582a07316ae0e8a8fb3b8fdc39d94842816`, AMD already supplies a **kernel-owned GTT BO** to supported ISP4 children. `isp_kernel_buffer_alloc` verifies the MFD child belongs to the same AMDGPU parent and requests 32 KiB alignment. `amdgpu_bo_create_kernel` reserves and pins the BO, obtains an aperture address, and creates a separate CPU mapping. The corresponding free calls unmap, unpin and drop the reference. This is a concrete kernel-only allocation design for comparison. The Jupiter version gate runs before those ISP4 children can exist. [Version gate and allocator](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/amdgpu/amdgpu_isp.c#L101-L126) · [ISP4 kernel allocation/free](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/amdgpu/amdgpu_isp.c#L250-L319) · [BO pin, GART and CPU mapping](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/amdgpu/amdgpu_object.c#L263-L316)

| Candidate mapping | What the target driver establishes | What still has to be established for ISP3 |
|---|---|---|
| AMDGPU global GTT/GART | TTM binds backing pages' device DMA addresses into the GPU aperture. `amdgpu_bo_gpu_offset` returns the offset in the appropriate domain. A one-page object with a cache mode other than `ttm_cached` can qualify for a direct AGP-aperture shortcut, so a successful allocator call alone cannot prove a particular page-table walk. [TTM bind](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/amdgpu/amdgpu_ttm.c#L935-L1038) · [Single-page exception](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/amdgpu/amdgpu_gmc.c#L181-L202) | **HYPOTHESIS for Jupiter** based on the Mero output/work-arena model. Jupiter’s ISP must actually decode the selected aperture and translation context for each reader/writer. No CPU VA or CPU physical address is interchangeable with this value. |
| Process GPUVM | `amdgpu_vm_bo_map` validates a mapping against the BO and inserts it in a particular GPU VM. For GC 10.3.1 the driver configures a 48-bit GPU virtual address size. Separately it sets a 44-bit DMA mask on the GPU parent. [Per-VM mapping](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/amdgpu/amdgpu_vm.c#L2019-L2040) · [GMC widths](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/amdgpu/gmc_v10_0.c#L795-L855) | The relevant ISP VMID/page tables, address-bit width and fault isolation. A 64-bit descriptor carrier, 48-bit process GPUVM, and 44-bit host DMA mask answer three different questions. |
| DMA-BUF / system IOMMU | The supported ISP4 importer converts a dma-buf into a pinned GTT BO and then obtains a GPU address. TTM maps the attachment for the importing device. The Mero custom video queue's attach, map and plane-formatting methods have different roles. [ISP4 import](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/amdgpu/amdgpu_object.c#L378-L416) · [Vendor queue methods](isp3-buffer-dependencies.md#three-distinct-memory-contracts) | A dma-buf FD holds a reference to an allocation. A mapped scatterlist is valid for the mapping's device. Neither supplies proof of a Jupiter ISP requester, cache state or a contiguous ISP-visible virtual extent. |

**Feasible offline design.** Keep the BO and DMA addresses private to the hypothetical kernel driver. A host-only test can supply synthetic segments and assert each format's planes fit within the owned allocation, with checked pitch × height, chroma rounding, non-overlap, address width and end-of-range arithmetic. A sensorless input would need its own documented format and capability before borrowing any output rule. Model the CPU producer, device reader, device writer and CPU consumer separately. For noncoherent/streaming mappings, track direction and the required CPU/device synchronization. A translation-cache flush or a ring fence cannot substitute for pixel visibility. [Linux DMA ownership and synchronization](https://docs.kernel.org/core-api/dma-api-howto.html) · [GART table flush versus GPU TLB](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/amdgpu/amdgpu_gart.c#L489-L506)

For teardown, model a queue that stops accepting submissions, receives frame completion or a documented device-quiesced condition, retires deferred response work and only then releases mappings. An error or timeout with outstanding DMA keeps the allocation owned until quiescence is established. Model and validate this ordering with synthetic responses. The Mero normal completion/stop distinction gives test cases. It supplies no Jupiter-specific drain acknowledgment or validated live recovery sequence.

A [file-only bound check](../scripts/decode_isp3_ring.py) now compares each nonempty plane in a single saved direct SEND_BUFFER with a supplied same-domain allocation. The [synthetic fixture](../tests/test_isp3_ring.py) covers an exact end, one-byte overrun and 64-bit overflow. It applies no unverified alignment rule to an input pixel plane.

## Recheck the new observations offline

Use the hashed ML2 files above. The commands inspect the normal output geometry and BO producer. They do not send commands to a GPU.

```sh
llvm-objdump -d --start-address=0xffffffff81a3ae1b --stop-address=0xffffffff81a3afdd vmlinux
llvm-objdump -dr --disassemble-symbols=amdgpu_gem_object_create,amdgpu_gem_gartmc_ioctl amdgpu.ko | rg 'amdgpu_(bo_pin|ttm_alloc_gart|bo_gpu_offset)|0x3b0|0x360'
```

To verify the public IVRS digest, save the linked hex dump as `F3B9E861E0CA.bin` and run this as offline Python.

```python
from hashlib import sha256
from pathlib import Path
import re

text = Path("F3B9E861E0CA.bin").read_text()
rows = re.search(r"^IVRS @ [^\n]+\n((?:    [0-9A-F]+: [^\n]+\n)+)", text, re.M).group(1)
table = b"".join(bytes.fromhex(row.split(":", 1)[1][1:48]) for row in rows.splitlines())
assert len(table) == int.from_bytes(table[4:8], "little") == 420 and sum(table) % 256 == 0
print(sha256(table).hexdigest())
for offset in (0x128, 0x147, 0x166, 0x185):
    assert table[offset] == 0xF0
    print(table[offset + 4:offset + 12].decode(), table[offset + 22:offset + 31].decode())
```
