# Which Mero ISP3 buffers need CVIP?

**CONFIRMED in build 9601.** One camera property gates the stream-initialization calls that import CVIP pages and publish their GPU address. The other branch reaches common stream setup without either callback. **STRONG EVIDENCE** that the stock ML2 image selects the CVIP branch by default. The later of two conflicting assignments in the image enables it. **UNKNOWN** whether the other branch can complete a memory-camera frame on Jupiter. It still depends on an ISP-visible frame address, working firmware, power, interrupts and buffer ownership.

The evidence comes from the ML2 x86 kernel (`f8891033b1f3b9cf9f25ef76d914173f1d43ff9a75df6764982207f0bd84f642`), its AMDGPU module (`ca31bf6b6751b6bcf8073daf7244a3dfb437e938c40905a5d5f04b94bc86cb9f`) and the 64-bit Android camera HAL (`907dd72aea4798cd6c5d115653abb246ac06b452c35c0d91d31960e7fd402eb2`). The camera driver is built into this kernel. Throughout this report a kernel instruction address written `81a…` or `816…` has `ffffffff` prepended. Module addresses are relative to ELF `.text`. Android library addresses are ELF virtual addresses. ## Callback inventory

At module `0x159535–0x159555`, `isp_sw_init` builds the following four-pointer table and passes it alongside the CGS graphics-services interface to `isp_init` at `0x15955c`. In the linked kernel, `isp_init` copies the four members and then checks that eight CGS operations, including memory and register access, are present. It does not invoke any of the four hooks at that point. The table lists every direct RIP-relative reference to the four resulting slots in this kernel's `.text` and `.init.text`. Aliasing through a computed pointer is a limit of the scan.

| Slot, install and consumer | When used | Dependency for a proposed independent frame |
|---|---|---|
| `+0x00 get_cvip_buff` → `ffffffff8317c200` at `81a91aa1`. `create_cvip_buf` loads it at `81a86ec3` and calls through R11 at `81a86ee1`. | First CVIP buffer setup when the cached CPU mapping is empty (`81a80982–81a8098c`). Missing callback or failed import returns an error to stream setup. | **Hard CVIP dependency** on the selected CVIP path. **Independent** of this particular call on the alternative stream-initialization branch. |
| `+0x08 cvip_set_gpuva` → `ffffffff8317c208` at `81a91a97`. The same creator loads it at `81a86fbc` and calls at `81a86fcf`. | After page import and a returned-capacity check. This announces the GPU address to the remote subsystem. | **Hard CVIP dependency** on this path. A local address allocator cannot perform the peer notification. |
| `+0x10 set_isp_power` → `ffffffff8317c210` at `81a91aac`. Calls at `81a9f47a` (`isp_req_clk`) and `81a9f6ae` (`isp_set_clock_by_smu`). | Clock selection at open, profile/state changes or close. `isp_clk_change` can request clocks at `81a9f243`. `set_isp_clock` uses the Mero SMU context. | **Adaptable** at the call boundary. **CONFIRMED scope.** The first two slots serve CVIP pre/post data and statistics. `isp_setup_cvip_buf` labels descriptor type 1 pre/post (`0x12000` bytes) and type 2 statistics (`0xa7a00` bytes). It calls `isp_fw_set_cvip_buf` at `81a80a6e` and `81a80b23`. The creator calls the two callbacks when it needs to construct this shared region. They are not evidenced as a mandatory pair of calls for each input or output image.

## Three distinct memory contracts

1. **CVIP-owned shared pages.** Module `get_cvip_buff` calls `amdgpu_bo_create_from_cvip` at `0x159346`. The latter calls kernel `cvip_gpu_get_pages`, attaches those pages to a TTM translation table, pins the BO and allocates GART space (module `0x1bd54`, `0x1be37`, `0x1be49`, `0x1be5e`). It returns the BO's GPU offset, a kernel mapping and a byte count based on 4 KiB pages. The page supplier reads CVIP driver state and supplies 4,096 pages in this build. On the CVIP side of the mapping, `cvip_is_alive` calls `cvip_map_gpuva` at `816d5909`. That routine obtains an IOVA and calls `iommu_map` at `816d563f` with protection 3 (read/write). Later `cvip_set_gpuva` checks the stored peer address and sends both that address and the GPU address via `ipc_sendmsg` at `816d5728`. The page list, GPU GART address, remote IOVA and CPU mapping are four different objects. The CVIP buffer release routine contains `dma_buf_kunmap` and `dma_buf_put` at `816d6c64/816d6c6c`. Ownership across cache invalidation, reset and all stream-close paths remains **UNKNOWN**. [Host transport comparison](host-interface.md)
2. **ISP-internal graphics scratch.** The CGS ops table at module `.rodata+0x3b678` supplies AMDGPU allocate/free, GPU-map/unmap, CPU-map/unmap and register I/O methods. Kernel `isp_gpu_mem_alloc` calls the allocate, GPU-map and CPU-map slots at `81aa0e5a`, `81aa0f66` and `81aa0fc4`. It keeps the handle, length, MC address and system mapping separately. The allocator passes `0x8000` alignment and heap offsets 0 and `0x10000000`. The firmware-work reserve has a distinct 11 MiB request, `0x8000` alignment and a different upper heap-offset argument, `0x100000000` at `81a84c61`. Those limits belong to these specific internal allocations. They do not describe every image plane or a CPU physical window. `isp_gpu_mem_free` dispatches to the CGS free slot at `81aa10bb`. These operations are **independent** of the CVIP shared-page API and **adaptable** in principle to a suitable kernel-owned BO. The exact Jupiter heap, ISP translation context and cache policy are **UNKNOWN**. [Historical AMD CGS allocation contract](https://github.com/torvalds/linux/blob/v4.9/drivers/gpu/drm/amd/include/cgs_common.h#L270-L302)
3. **Android frame buffers.** Mero’s `map_stream_buf` calls `map_img_addr` at `81a3aae6`. That helper derives image-plane descriptors from an incoming MC address and format. `isp_map_sys_2_mc` separately constructs plane descriptors and addresses from an existing handle. Neither helper establishes a new device DMA mapping. The custom VB2 operations table at `ffffffff82500b78` does have `dma_buf_attach` and detach, but its `amd_map_dmabuf` returns zero with optional logging and `amd_unmap_dmabuf` simply returns after optional logging. The queue can also select a vmalloc ops table (`init_vb2q`, `81a425e3–81a425f8`). A successful map-method return on this vendor path cannot establish ISP-accessible memory on another board.

### Where Android gets the frame address

The build sets `ro.swr_enable=false` and its stock `init.mero.rc` selects GBM gralloc in that configuration. The 64-bit library member hashes below match the vendor image inventory. [Image provenance](../evidence/artifacts.md) · [Per-file hashes](../evidence/host-index.tsv)

| Layer | Static evidence |
|---|---|
| Camera HAL | `Q_drvReq` calls `getMCaddr` at `0x8d188/0x8d1f9`. `getMCfromBuf` invokes a gralloc module method at `0x770bf` to request the address associated with a buffer handle. |
| `gralloc.gbm.so` and `libgbm.so` | Gralloc's HMI relocation at `0x8bd0` selects the provider at `0x5400`. Its matching branch calls `gralloc_gbm_bo_get_mc` at `0x55b2`, which calls `gbm_bo_get_mc` at `0x4339`. In libgbm, the backend dispatch (`0x50e3`, target installed at `0x5414`) selects a DRI image operation at `0x622f`. |
| `gallium_dri.so` and `libdrm_amdgpu.so` | The `DRI_IMAGE` table relocation at `0xc20ce8` selects `0x560130`, which returns a cached MC address only when its validity flag is set. Elsewhere in Mesa two BO paths call `amdgpu_bo_get_gartmc` at `0x54e67b/0x54f104` and set their validity flag on success. The transfer of the value between those internal objects remains **UNKNOWN** for an individual buffer. In libdrm the helper issues its private query at `0x5d30`. Mero AMDGPU's matching ioctl descriptor at `.rodata+0x27e0` points to `amdgpu_gem_gartmc_ioctl` at `.text+0x21040`, which looks up a GEM handle and returns a stored BO field. |

**Portability limit.** The matching Neptune module lacks the `amdgpu_gem_gartmc_ioctl` symbol. Its public UAPI provides GEM VA mapping and lacks the named Mero GART-MC query. A frame buffer obtained through a process GPU VM, a CPU VA or a generic dma-buf attachment cannot simply supply a vendor MC address. A possible replacement would need one identified ISP DMA master and translation domain, a confirmed address width/plane layout, a mapping valid for its entire lifetime and synchronization of ownership. Memory camera inputs are device reads, captured outputs are device writes, and any shared bidirectional control data needs its own contract. The Mero remote mapping's read/write permission does not specify frame DMA direction or CPU cache coherency. Timeout, completion and teardown would all need to retire outstanding accesses before reuse. None of these Jupiter-specific prerequisites has been established by the branch analysis. [Neptune UAPI](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/include/uapi/drm/amdgpu_drm.h#L43-L85) · [Linux DMA address spaces and ownership](https://docs.kernel.org/core-api/dma-api-howto.html) · [DMA-BUF synchronization](https://docs.kernel.org/driver-api/dma-buf.html)

## Recheck without a device

Use the hash-matched regular files from the existing offline extraction. The first command enumerates the four static slot references across the executable kernel sections. The second locates the shipped Android vtable target. The final command displays both definitions of the camera property in their original order. [Extraction guide](../reports/reproduction.md)

```sh
llvm-objdump -d --no-show-raw-insn -j .text -j .init.text ml-vmlinux | rg -i '0xffffffff8317c2(00|08|10|18)\b'
llvm-readelf -rW camera.raven.so | rg '00000000000d0fd0'
rg -n '^persist\.hardware\.camera\.(enable_cvip|timestamp_from_cvip)=' system/system/build.prop
```
