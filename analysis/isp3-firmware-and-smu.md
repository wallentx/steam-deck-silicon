# Which Mero ISP firmware and power interfaces would Jupiter need?

The later [SMU image comparison](isp3-smu-compatibility.md) distinguishes the host message names below from the actual firmware handlers. Four ISP rows are empty on Jupiter's ordinary AMDGPU-facing mailbox. [ISP executable and boot analysis](isp3-firmware-boot.md)

**CONFIRMED in the ML2 build 9601 binaries.** The two firmware files have different contents and different consumers. The AMDGPU module stages the wrapped ISP image for the PSP firmware-loading path. The camera ioctl requests the separate RAM file and releases it on the success path without passing its contents to the ISP. The five SMU message numbers used by the Mero ISP callbacks agree with Jupiter's published mapping, although their drivers expect different SMU interface versions. Acceptance of this firmware and power sequencing on Jupiter remain **UNKNOWN**. [Input archive and hashes](../evidence/artifacts.md) · [Offline verifier](../scripts/inspect-isp3-build.py)

The following linked kernel offsets use `K:` relative to `0xffffffff81000000` in the original x86 ELF, SHA-256 `f8891033b1f3b9cf9f25ef76d914173f1d43ff9a75df6764982207f0bd84f642`. Module offsets use `M:` relative to `.text` in the Mero `amdgpu.ko`, SHA-256 `ca31bf6b6751b6bcf8073daf7244a3dfb437e938c40905a5d5f04b94bc86cb9f`. They locate instructions in these Mero files for offline disassembly.

1. **Registration and staging.** In `isp_sw_init` the ASIC check at `M:159561` selects the Mero firmware request at `M:159578`. The code compares the file length to its header, records ucode ID `0x21` at `M:1595b2`, stores the firmware pointer, and adds the payload size rounded up to 4 KiB to the staging allocation. A failed request takes different paths according to the firmware-loading mode. A returned initialization status alone cannot prove firmware execution.
2. **PSP dispatch.** The generic module routines `amdgpu_ucode_init_bo`, `psp_np_fw_load` and `psp_execute_np_fw_load` connect staging to the PSP load-IP-firmware operation. The last routine constructs command ID 6 at `M:c81ad`. Its allowed-type table includes index `0x21`. At `M:c8204` that index selects `0x10` from `.rodata+0x29e18`. Neptune independently names command 6 `LOAD_IP_FW` and type 16 `GFX_FW_TYPE_ISP`. Matching identifiers establish a shared command vocabulary. Jupiter still lacks an ISP3 registration, a verified per-board image, a PSP acceptance result and an established trusted-memory allocation. [Neptune command 6](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/amdgpu/psp_gfx_if.h#L94) · [ISP type 16](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/amdgpu/psp_gfx_if.h#L227) · [Neptune PSP type lookup](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/amdgpu/amdgpu_psp.c#L3265-L3275)
3. **The RAM-file distinction.** In `isp_ioctl`, a state value of 1 leads to `request_firmware` for the literal RAM filename at `K:a4607a/a46088`. Successful lookup takes `K:a46824`, optionally logs at `K:a46f91–a46fbc`, and joins `release_firmware` at `K:a4683f`. That path then advances the camera-driver state to 2. It never dereferences the returned firmware's data or length. Separately, `set_fw_bin_imp` can allocate and copy a caller's bytes at `K:a93368–a93393`. The named RAM-file lookup has no observed edge to that API. The claim that this lookup uploads a second copy of the executing firmware is **DISPROVEN for this path**. Whether another configuration uses the raw image elsewhere is **UNKNOWN**.
4. **Code destination and readiness.** `isp_fw_boot` expects driver state 2. It obtains command/response, code, stack and heap bases from the work-buffer layout (`K:a8b9f5–a8bc2b`), examines TMR configuration, and has a branch with linked value `0xf41ec00000` plus a 2 MiB range (`K:a8bdbc–a8be33`). Other paths use values read from the configured mapping. It reaches `isp_hw_ccpu_enable` at `K:a8c111` and polls for readiness with timeout. This is evidence about the Mero device's address space. Neither that value nor the wrapper's zero load field identifies a CPU physical destination on Jupiter. [Ring and completion evidence](isp3-frame-evidence.md)

## SMU comparison

The Mero module uses driver indices first. `mero_get_smu_msg_index` (`M:1b67f0`) checks the validity word and reads the mapped ID from eight-byte rows in `mero_message_map`, `.rodata+0x5fb00`. The clock callback invokes the SoC, XCLK and ICLK requests in that order. The power callback uses a Mero tile-mask argument of `0x1f`. Its applicability to Jupiter's tiles and the board's power, voltage, reset and interrupt dependencies is **UNKNOWN**. [Matching Neptune message header](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/pm/swsmu/inc/pmfw_if/smu_v11_5_ppsmc.h#L39-L58) · [Neptune callback mappings](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/pm/swsmu/smu11/vangogh_ppt.c#L86-L106)

|---|---:|---:|---:|

| ISP tile power up | `0x67` | `0x07` | `0x07` |

**CONFIRMED build-level mismatch.** For the module's Mero ASIC value `0x1c`, `smu_v11_0_check_fw_version` selects index `0x1c − 0x15 = 7` at `M:1b360b–1b3634`. The corresponding word in `.rodata.cst32+0x3fc` is **2**. Neptune's Van Gogh setup assigns driver interface **3**. The discovery MP1 revision is 11.5.1 on Mero and 11.5.0 on the saved Deck. These are expected driver interface versions and hardware IP revisions respectively. The Mero version-check routine logs a mismatch and retains the prior query status. A difference in the compiled expectations establishes neither rejection nor the negotiated firmware version on a particular boot. ## Source availability and reproduction

Magic Leap's public hardware notice identifies Linux 5.4.19, an offer for the corresponding source, and the May 2022 list of modified files. The listed `drivers/media/platform/amd-isp3/` subtree includes the camera interface, command/response, memory allocator, power and register definitions. The file list predates build 9601. The exact R64 source, revision and build configuration were unavailable. GitHub indexed-code searches for `isp_is_mem_camera`, `amd-isp3` in Makefiles and `mero_ip_offset.h` returned no public match. `set_fw_bin_imp` does match AMD's published **ISP4** header, and AMD's version-1.0 branch already contains an ISP4 boot implementation. These are useful structural comparisons. They cannot establish binary compatibility. The public Magic Leap kernel repositories inspected target earlier Lumin releases.
