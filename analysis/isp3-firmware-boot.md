# ISP3 executable images, entry evidence and boot readiness

**CONFIRMED in ML2 build 9601.** The wrapped image and the raw RAM image both contain a windowed Xtensa ISP program with its own command receiver. They require different sizes for the same frame-info command. Treat them as distinct builds. The shipped host path stages the wrapped image for the PSP. One camera-state transition requires a successful lookup of the RAM file, then releases it without consuming its contents. This supplies no evidence that the two files execute as consecutive stages. [Separate load chains and exact hashes](isp3-firmware-and-smu.md) · [Independent receiver comparison](isp3-memory-input.md)

| Question | Evidence and limit |
|---|---|
| Which CPU? | **STRONG EVIDENCE** for an Xtensa LX7 configuration. The two images contain the exact identifier `isp3p0_lx7` at file offsets `0x7c04` (wrapped) and `0x24adc` (RAM), adjacent to XOS core-configuration diagnostics. Their code has a windowed ABI. At body offset 0 each has four `s32e` instructions and `rfwo`; at `+0x40`, four `l32e` and `rfwu`. This matches the architecture's four-register window overflow/underflow vectors. [Xtensa vector definitions](https://github.com/torvalds/linux/blob/8d3ae59288f1e7d58d76558a6ee96d533bc5019f/arch/xtensa/kernel/vectors.S#L705-L725) |
| What is the entry point? | **CONFIRMED** the first bytes are exception-vector code. The wrapped body starts at file `+0x200`; the RAM body starts at zero. A linked code origin of `0x60000000` explains table entries and their string/code cross-references in both builds. Frame-info handlers can be located at `0x6008d718` and `0x60092e9c`. The actual reset PC, reset ROM selection and first instruction on a Jupiter boot remain **UNKNOWN**. The wrapper load field is zero. None of these observations identifies a Jupiter physical entry address. |
| What did the PSP receive? | **CONFIRMED software path.** Mero `isp_sw_init` stages ID `0x21` from `mero_isp.bin`; `psp_execute_np_fw_load` maps it to PSP type 16. The outer payload has a valid CRC, the inner signed flag is 1, and its body SHA-256 matches the stored hash. The RAM file lacks that wrapper and diverges at body byte 420. Trust-anchor compatibility, a successful signature check and an ISP assignment in Jupiter's recorded 10 MiB PSP TMR remain **UNKNOWN**. The host-side raw-image setter and the RAM-filename lookup are separate call paths. [Header offsets, PSP translation and RAM-file release](isp3-firmware-and-smu.md#firmware-images-and-their-consumers) |
| How is control memory arranged? | **CONFIRMED host layout.** In the original x86 kernel the work-buffer helpers at `K:a920f0/a92130/a92170` describe code 2 MiB, stack 512 KiB at `+0x200000`, heap `0x580000` at `+0x280000`. Ring allocation follows in that layout. The boot routine also examines preconfigured TMR windows and has a fallback linked constant. Kernel work-area geometry does not measure where the PSP placed executable code on a particular boot. The driver requests a larger initial backing allocation. [Allocation evidence](isp3-dma-portability.md) |
| What signals readiness? | **CONFIRMED** `open_camera_imp` can call `isp_ip_pwr_on` and `isp_fw_start` at `K:a93de8/a93e6f`. `isp_fw_boot` checks software state 2, sets up command/response rings, then calls `isp_hw_ccpu_enable` at `K:a8c111`. The status loop tests bit 1 of its sampled word at `K:a8c139/a8c199`, sleeps 1–2 ms between polls and passes 10,000 to the millisecond timeout helper. Embedded kernel configuration has `CONFIG_HZ=250`; `isp_is_timeout` scales tick differences accordingly (`K:aa5360–aa53ad`). The ready branch sets state 3 at `K:a8c1fa`. The timeout branch records a failure. This witnesses neither a ready transition nor a frame on Jupiter. |

`K:` is relative to `0xffffffff81000000` in the hash-identified original x86 ELF. To reproduce the vector identification, disassemble each body **at the actual vector boundary** (file `0x200/0x240` for the wrapped file and `0/0x40` for RAM) with GNU Xtensa objdump 2.44, `-D -b binary -m xtensa -EL`. Linear disassembly starting inside padding can lose instruction alignment. The existing verifier checks file identity, nested lengths and digests. It now also follows each command-table pointer and the PC-relative size literal. Exact decoded lengths are 4,728 and 4,656 bytes. [Verifier](../scripts/inspect-isp3-build.py) · [Archive provenance](../evidence/artifacts.md)

**Verdict for Jupiter.** Matching ISP3 inventory and a known PSP firmware-type number make this a relevant implementation reference. Neither image has evidence of authentication, boot readiness or successful execution on Jupiter. A further concrete incompatibility is the lack of ISP power/clock handlers on the ordinary graphics mailbox in Valve's packaged SMU. [SMU compatibility](isp3-smu-compatibility.md)

GNU Binutils 2.44 was built for static analysis in a private scratch directory. The release tarball SHA-512 was checked against the publisher’s manifest. [Release checksums](https://sourceware.org/pub/binutils/releases/sha512.sum)
