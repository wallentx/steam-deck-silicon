# Can the LCD Deck ISP process a frame from memory without CVIP?

**UNKNOWN on Jupiter. CONFIRMED in Mero's shipped driver:** stream setup can bypass both CVIP buffer callbacks. The skipped buffers carry camera metadata and statistics. Ordinary image buffers use a separate, Mero-specific graphics-memory interface. There is also a more immediate obstacle on the normal memory-camera path. Logical camera 3 starts with firmware ring 4, and the command queue rejects that value. No inspected production entry point both supplies an input image and assigns that camera a usable ring. [Buffer and callback audit](isp3-buffer-dependencies.md) · [Frame call graph](isp3-frame-evidence.md)

The offline assessment used the Deck's recorded F7A0133 discovery data, Valve's matching Neptune kernel and Magic Leap 2 OS 1.12.1 build 9601. A later live boot verified both ISP bases, the loaded AMDGPU build ID and the SMU interface version. A byte-identical ISP inventory entry establishes the hardware ID, IP version and two register-base descriptors. The captured Deck boot registered no ISP block. The Mero camera driver is built **into** the x86 kernel: `amd_capture.ko` is a name in `modules.builtin`. The separately shipped loadable object examined here is Mero's `amdgpu.ko`. [Live Deck measurements](../evidence/deck-live/isp3-boot-check.md) · [Registration evidence and file hashes](followup-isp.md)

## The shortest path the binaries support

1. **Register and configure.** Mero's `nv_set_ip_blocks → isp_sw_init → isp_init` installs the graphics and power hooks. `amd_capture_probe` registers physical cameras 0 and 1. The HAL reads `persist.hardware.camera.enable_cvip` and passes the setting to the camera driver. The HAL fallback is false. The shipping property file sets it false at line 75 and true at line 163. Android 10's duplicate handling favors the later value, and persistent state can override it. The value on a running ML2 was unavailable. [Property chain and stock configuration](isp3-buffer-dependencies.md)
2. **Prepare the firmware and rings.** AMDGPU stages `mero_isp.bin` for the PSP. The ISP boot code prepares four command and four response rings, obtains work-memory bases and waits for the ISP control CPU to become ready. The distinct RAM file's camera ioctl requests and releases it without consuming its bytes on the traced path. Both images contain Xtensa HAL evidence. No compatible Jupiter firmware acceptance, destination or readiness response has been established. [Load paths and SMU comparison](isp3-firmware-and-smu.md)
3. **Select the stream.** With the CVIP field clear, `isp_init_stream` skips the CVIP sensor, shared buffers and slice setup, then joins `isp_setup_stream`. The memory-camera predicate accepts logical ID 3. Its backing camera for profile lookup is 1, yet its firmware ring from reset is 4. `isp_get_stream_id_from_cid` preserves an already assigned ring, and a physical camera with sensor type 4 also qualifies for the memory predicate. Neither exception establishes a stock memory-input producer. [Reset, alternate camera types and insertion bound](isp3-frame-evidence.md)
4. **Compare with a complete output path.** Ordinary capture submits a frame-control command with output descriptors. An interrupt wakes the response handling path, a frame-done response completes the frame, and V4L2/HAL can dequeue the output. Firmware also names a frame-info command that could consume input. The corresponding literal uses audited in the shipped kernel are comparisons or diagnostics. The Android `input_buffer` branch leads to host reprocessing, including a scaler and JPEG paths. Both shipped camera configurations advertise zero input streams. Their 640 × 480 minimum applies to advertised YUV **output**. YUV422 loopback diagnostics describe bypass of the core. The input dimensions, pixel format and transform for an independent sensorless ISP3 workload remain **UNKNOWN**. [Commands, descriptors, IRQ, dequeue and HAL evidence](isp3-frame-evidence.md)

## Dependency matrix

Classification describes the named software path on build 9601. **Independent** means the cited operation has an observed path without a CVIP call. **Adaptable** identifies a concrete interface to port with outstanding validation. **Hard CVIP dependency** means that particular operation consumes CVIP-owned resources. **Unknown** identifies a missing contract or producer. These classifications provide no hardware authorization or proof of operation on Jupiter.

| Dependency and stage | Class | Evidence and limit |
|---|---|---|
| Register ISP3 / install four callbacks at probe | **Independent** | **CONFIRMED.** Installing the callbacks requires a valid graphics-services device. That operation does not invoke either CVIP buffer callback. Jupiter's kernel skips 3.0.0 registration. [Probe trace](isp3-buffer-dependencies.md) |
| CVIP camera/statistics buffers and GPU-address publication at stream setup | **Hard CVIP dependency** on the enabled branch | **CONFIRMED.** `get_cvip_buff` imports CVIP-owned pages. `cvip_set_gpuva` sends their GPU address over IPC. The disabled branch bypasses both. Replacing them with unrelated pages would lose the peer and its ownership contract. [All four callback installations and observed consumers](isp3-buffer-dependencies.md) |
| ISP command/response storage and internal graphics scratch | **Adaptable** | **CONFIRMED** Mero uses graphics-services allocation, GPU and CPU mappings and teardown. A Jupiter equivalent must supply the ISP-visible address space, alignment, lifetime and CPU/device synchronization for those allocations. [Allocation and teardown](isp3-buffer-dependencies.md) |
| Pixel-buffer handoff between gralloc, GPU and ISP | **Unknown** | **CONFIRMED** Mero's ordinary path gets a GPU memory-controller address via a vendor GEM operation absent from Neptune. A DMA-BUF handle or a GPU process VA alone does not establish ISP translation, DMA direction, fences or cache ownership. Capture output and memory input need separate ownership transitions. [Address domains and portability limits](isp3-buffer-dependencies.md) |
| ISP power and clocks at bring-up and teardown | **Adaptable** at the message interface | **CONFIRMED** all five translated IDs agree. Mero's driver expects SMU interface 2. Jupiter's running driver and firmware both reported 3. The tile mask, rails, reset ownership and applied clocks on this Deck are **UNKNOWN**. The mismatch alone does not imply firmware rejection. [Numeric comparison](isp3-firmware-and-smu.md) |
| PSP firmware acceptance and trusted-memory handoff | **Unknown** | **CONFIRMED** Mero's wrapped body digest and ISP firmware type. Jupiter's firmware trust, placement and boot outcome remain unverified. [Two image formats and consumers](isp3-firmware-and-smu.md) |
| Backing-camera profile, calibration and sensor data | **Unknown** for sensorless use | **CONFIRMED** logical camera 3 borrows physical profile 1 in the stock open path. The release includes sensor-specific calibration files. Which calibration, sensor timing or board resources a memory-fed route can omit remains unverified. [Profile and sensor providers](isp3-frame-evidence.md) |
| Memory input, ring assignment and output completion | **Unknown** | **CONFIRMED** the cold logical-camera-3 path reaches a rejected ring. The ordinary V4L2 output route provides a positive control for frame completion. No same-frame input-to-output evidence on the memory route. [Frame graph and exceptions](isp3-frame-evidence.md) |
| ISP interrupt delivery | **Independent** of CVIP's PCI mailbox in the observed driver path | **CONFIRMED** the Mero camera code registers GPU interrupt-handler client 5 and four source IDs. No saved Jupiter capture establishes routing or delivery of those sources. [Interrupt and response evidence](isp3-frame-evidence.md) |

The Android reprocessing path is **independent** of the two CVIP buffer callbacks in the observed host scaler calls. Its input validation and software scaling do not supply the ISP firmware with an input descriptor. [HAL vtable and output formats](isp3-frame-evidence.md#android-reprocessing-is-a-separate-path)

## Offline milestone

From the repository root, run `python3 scripts/inspect-isp3-build.py WORK` against the extraction layout in the reproduction guide. The executed verifier checks five original file hashes and decodes the branch targets, reset-ring values, message IDs and firmware digest directly from those files. On build 9601 the camera results are `[1, 2, 3, 4]` with an insertion bound of `< 4`. The verifier works on file bytes and produces no camera traffic. [Verifier](../scripts/inspect-isp3-build.py) · [Extraction guide](../reports/reproduction.md)

**Single most informative next experiment.** Trace one host-supplied input plane through the corresponding R64 ISP3 source. Start at the input descriptor producer. Require a ring assignment accepted by the inserter and a consumer that ties the completed output to that submission. Include the alternate physical-camera sensor-type configuration. These are specific symbols and conditions to search for in Magic Leap's source offer. With such a path identified, a host-only descriptor test could use ordinary test memory and recorded responses to validate the producer, ring selection and buffer lifetime. The source and a known-good memory-frame trace were unavailable here. A positive source result would establish a software path to assess for Jupiter. Testing physical firmware acceptance, power or DMA would still require a separate proposal and approval. [File list and source offer](isp3-firmware-and-smu.md#source-availability-and-reproduction)
