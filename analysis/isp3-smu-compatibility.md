# The ordinary graphics mailbox has different ISP handlers

**CONFIRMED in the distributed firmware.** F7A0133 and Mero name five matching SMU messages in their host drivers. On the graphics mailbox actually selected by these drivers, the two ISP power and two ISP clock handlers are populated in Mero's firmware and **empty in Jupiter's**. The SoC clock and three identification/control handlers remain populated in both. The Deck firmware's dispatcher stages status `0xfe` (unknown command) for a null entry. **STRONG EVIDENCE** that transferring Mero's power/clock callbacks unchanged cannot bring up ISP3 through this stock Jupiter interface. No SMU request was sent. This does not determine the physical condition of the ISP or every pre-OS power policy. [Offline comparator](../scripts/compare_isp3_smu.py) · [Live Jupiter version](../evidence/deck-live/isp3-boot-check.md)

## Identify the firmware and the mailbox

1. **Inputs.** Valve Jupiter LCD F7A0133 capsule SHA-256 `c8b1e749ad709bf20899eed59bd9012a8482b55003d2785134f0b17876a240d9`. Mero ML2 1.12.1/9601 regular BIOS `demophon_bios.FD`, SHA-256 `f4b050e9b7f518b084b4184b7818a7e03cdabc975f20357d99a11f66469c5b62`. Coreboot names PSP directory types `0x08` and `0x12` SMU firmware and second SMU firmware. In each image, both directory copies give identical corresponding entries. [Valve source package](steam-deck-applicability.md) · [ML2 BIOS provenance](../evidence/revision-bios.md) · [Directory types](https://github.com/coreboot/coreboot/blob/8329c70b1077e36702410503972d3925f7b57a2d/src/vendorcode/amd/psp/psp_directory.h#L76-L86)
2. **Bounds.** The type-8 wrappers start at capsule offsets `0x191a70` (Deck) and `0x152c00` (Mero). Both are `0x40200` bytes including a 256-byte header and a 256-byte trailer. SHA-256 over the intervening `0x40000` bytes is `878daa1d0628ed60507b6e3b6a242a11f58044aaa739664d4d536e0beff7855a` and `4b1a09514d44cd3747fb216ed2d4a9a6f2fe9177e950a9e626d0802237d8aab0`, respectively. All following table offsets are relative to this type-8 body. All handler values are linked firmware addresses.
3. **Host correspondence.** In Mero build 9601, `smu_v11_0_send_msg_with_param` (`amdgpu.ko .text+0x1b30d0`) uses the same three MP1 mailbox selectors that Neptune's `vangogh_set_ppt_funcs → smu_v11_0_init_msg_ctl` assigns. The firmware's port-0 descriptor at `+0x62ac` matches their argument, response and message byte offsets. Neptune configures one argument register. This identifies the port independently of finding superficially similar entries elsewhere in the image. [Matching Neptune initialization](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/pm/swsmu/smu11/smu_v11_0.c#L2096-L2110) · [Van Gogh selection](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/pm/swsmu/smu11/vangogh_ppt.c#L2638-L2646)
4. **Dispatch.** The port-0 table pointer is at Deck `+0x73d0` and Mero `+0x7420`. Both point to `+0x6358`; the dispatcher indexes eight-byte rows by message ID. The counts are 90 and 85, so all rows below are in range. In Jupiter the load and null test occur at `+0x1036–0x104e`; `+0x104f–0x1057` stages `0xfe` for a null function. The deferred reply path at `+0x11f0` flushes staged responses. Static dispatch is the evidence here. No rejection was observed live.

| Request | R64 host argument | Mero port-0 handler | Jupiter port-0 handler | Compatibility |
|---|---|---:|---:|---|
| ISP down `06` / up `07` | `set_isp_power` sends a single tile mask, `0x1f`; the boolean selects down/up. | `45f60 / 46048` | `0 / 0` | **DISPROVEN on this table** that the Jupiter entries implement the corresponding tile requests. |
| ISP ICLK `0e` / XCLK `0f` | `set_isp_clock` forwards separate 32-bit requested minima. | `45db4 / 4cf00` | `0 / 0` | **DISPROVEN on this table** that these two named Jupiter messages dispatch to ISP clock handlers. |
| SoC minimum clock `17` | First request in the Mero clock callback. Neptune also passes its scalar minimum for `SMU_SOCCLK`. | `45c00` | `45458` | **CONFIRMED** shared high-level operation and populated slots. Applicable ranges and achieved frequencies remain **UNKNOWN**. |
| Test `01`, firmware version `02`, interface version `03` | Positive controls for table identity. | `1cd0c / 1cd24 / 1ced4` | `1ccdc / 1ccf4 / 1cef4` | Test increments the argument. Version reads the first four image bytes. Interface-version control returns **3 in both packaged images**. |

Nonzero cells above have metadata word 6. All four empty Jupiter cells have both words zero. Eligibility checks in the dispatcher still apply even to populated rows. The values in the table are sufficient to verify presence/absence without interpreting a handler implementation. Interpreting the second 256 KiB Mero body at linked offset `0x40000` places valid Xtensa entries at the four pointers, with calls back into the first image. **STRONG EVIDENCE** under this mapping: the down handler reads the supplied argument at `0x45f65`, extracts its low 16 bits at `0x45f70`, and its path tests several individual bits. The ICLK and XCLK handlers both test feature number 51 (`0x45db7` region and `0x4cf03`). There is no equivalent argument/units contract to compare in the four empty Jupiter rows. Other firmware ports have separate dispatch tables and eligibility rules; a matching numeric selector there does not establish a supported graphics-driver operation.

## Reply codes, feature bits and versions

**CONFIRMED host contract.** Mero sends the SoC, XCLK and ICLK minima in that order and forwards one scalar for each. Its camera diagnostics identify SCLK/ICLK/XCLK; the separate ISP-firmware notification scales three stored clock values by 1,000 at `K:a9167f–a91699`. That camera message has a different recipient. No Jupiter ISP-specific range, unit conversion or safe clock follows from it. The R64 module's `mero_feature_mask_map` at `.rodata+0x601e0` maps driver feature indices `52h/53h/54h` to bits **51/52/53** (ISP DPM, A55 DPM, CVIP DSP DPM), the same bits named by Neptune. Neither a feature-name mapping nor a shared SoC clock request establishes an enabled ISP rail. [Driver IDs and callback offsets](isp3-firmware-and-smu.md#smu-comparison) · [AMD feature bits](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/pm/swsmu/inc/pmfw_if/smu_v11_5_pmfw.h#L83-L89)

The common response codes are success 1, failure `ff`, unknown `fe`, bad prerequisite `fd` and busy `fc`. In Mero `smu_v11_0_send_msg_with_param` the branches at module `+0x1b31fa–0x1b3292` translate busy to `-EBUSY`, bad prerequisite to `-EINVAL`, and unknown to `-ENOENT`. Neptune's published v1 decoder translates unknown to `-EOPNOTSUPP`. Its generic unrecognized reply and zero/no-response cases are also distinct. Host error numbers should not be used interchangeably between releases. [Response constants](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/pm/swsmu/inc/pmfw_if/smu_v11_5_ppsmc.h#L27-L32) · [Neptune decoder](https://github.com/Jovian-Experiments/linux/blob/31504582a07316ae0e8a8fb3b8fdc39d94842816/drivers/gpu/drm/amd/pm/swsmu/smu_cmn.c#L253-L291)

**Correction to the interface-version comparison.** The Mero **driver** expects 2. Its packaged firmware's ID-3 handler places 3 in the reply at `+0x1ced9`. Jupiter does the same at `+0x1cef9`. ID 2 yields `0x053f4000` on Mero and `0x063f0f00` on Jupiter; the latter matches the complete version in the owner's boot log, which also reports interface 3. Mero's runtime was not sampled. The concrete obstacle is the missing handlers on the stock Deck graphics interface. Runtime patching of the table was not measured. Whether another documented board policy exists, or whether the ISP rails and reset are implemented, remains **UNKNOWN**.
