# Where a host-supplied frame stops in Mero ISP3

**CONFIRMED in the shipped code.** On a freshly initialized Mero camera context, logical camera 3 passes the memory-camera predicate, inherits camera 1 for profile lookup, and has firmware stream ID **4**. The running scheme allocates four rings numbered **0 through 3**. The command insertion routine rejects ID 4. The built-in capture driver registers two physical cameras, IDs 0 and 1. No inspected ordinary camera entry point assigns a usable ring and supplies a host-input frame to camera 3. **UNKNOWN** whether a private configuration or a different producer closes both gaps. This prevents presenting the sensor capture graph below as a demonstrated memory-input workload. [Prior ISP evidence and source provenance](followup-isp.md) · [ML2 build 9601 archive](../evidence/artifacts.md)

### Can a registered camera keep its ring and acquire memory type 4?

**CONFIRMED code path.** A physical ID 0 or 1 with sensor type 4 would satisfy the memory-camera predicate while retaining its ordinary ring. At `K:a93b80–a93b9c`, `open_camera_imp` initializes the physical type to zero and queries `get_camera_dev_info_imp`. On success it copies the returned descriptor’s dword `+0x40` into the camera slot (`K:a93d68–a93d6b`). The stock IMX577, S5K3L6 and S5K3LU `get_sensor_hw_parameter_*` callbacks all return **0** in their first dword (`K:a690e2`, `K:a6df62`, `K:a70c22`). The query copies that dword to the cached type at `K:a9a00d`. If the sensor query fails, the per-camera cached types initialized by `ispm_sw_init` are also zero. The separate explicit store of **4** at `K:a93d9b` requires the requested logical ID to equal **3** (`K:a93d87–a93d8e`).

**UNKNOWN effective override on a booted ML2.** A second source can supersede those sensor results. `get_camera_dev_info_imp` replaces descriptor dword `+0x40` when the signed `rear_sensor_type`, `frontl_sensor_type` or `frontr_sensor_type` setting differs from `−1` (`K:a9a076`, `K:a9a0ab`, `K:a9a114`, shared store `K:a9a0b9`). All three start at `−1` (`K:a783df`). Interface slot `+0x310` exposes `set_drv_settings_imp`, which can replace the settings block (`K:a930c4`, `K:a9b506`). No inspected stock camera configuration or sensor provider supplies a value of 4 to a physical camera. An external settings caller remains possible. A valid ring in that hypothetical case would clear the ring obstacle only. The shipped output-queue graph and the command-issuer search below still supply no ordinary host-input descriptor producer for that ring.

## The frame-info command has a receiver and no identified ordinary issuer

**CONFIRMED.** `isp_dbg_get_cmd_str` identifies `0x02050002` as `CMD_ID_SEND_FRAME_INFO` (`K:aa380f`, `K:aa3da3`). In `mero_isp.bin`, offsets `0x13e50`, `0x13eb0` and `0x15bc0` identify a frame-info structure size check, a failure delivering host frame info to the pipeline manager, and `StreamMgrCmdSendFrameInfo`. Other firmware diagnostics place raw read DMA and YUV422 post-loopback inside the design. The loopback messages specifically describe skipping the core pipeline. They establish neither a diagnostic-only use nor a general image-processing interface. [Firmware identities and offsets](followup-isp.md)

**CONFIRMED bounded negative.** Across all `0x12012f1` bytes of the x86 kernel `.text`, the little-endian frame-info command value appears five times. At `K:a875ab` and `K:a887c3` the command infrastructure *compares* an existing ID. At `K:a88914` and `K:a8896c` it passes the constant into debug output. At `K:aa380f` it looks up a name. None of those instructions originates a frame-info command. The positive control `CMD_ID_SEND_FRAME_CTRL` (`0x02050001`) has a direct issuer at `K:a9029f`. The frame-info value has zero literal occurrences in the Mero AMDGPU module’s `.text` or the 64-bit camera HAL’s `.text`. The interface slot `+0x428` contains `fw_cmd_send_imp` (`K:a931e2`), which returns zero without enqueueing work (`K:a9cfc0–a9cfcc`). The separate `online_tune_imp` does call generic command senders. Dynamically supplied or computed IDs and other clients remain **UNKNOWN**. A name lookup or a success return from that stub does not establish submission.

## One complete output-buffer path in the shipped camera stack

The rows show static control flow, including the function-pointer assignments needed to cross driver layers. **CONFIRMED** means the compiled branch exists. No frame execution was observed during this investigation.

| Stage | Verified edges and observable limits |
|---|---|
| 1. Queue an ordinary camera request | In `camera.raven.so`, `amdCamera3DriverInterface::Q_drvReq` gathers per-buffer details at `H:8d101` and calls `ioctl` at `H:8d302`. The built-in camera `_ioctl_default` matches the same request and calls `enq_request` at `K:a44561`. It checks the first output buffer and user pointer, copies the descriptor, and calls `vb2_qbuf` at `K:a3a542`. `buffer_prepare` calls `map_stream_buf`, which calls `map_img_addr`; the latter fills the output format, dimensions, pitches and plane addresses. Invalid formats have a default-format branch. |
| 2. Send one frame control | `buffer_queue` selects the internal ISP subdevice operation at `K:a44fa8`. `isp_ioctl` retrieves interface slot `+0x70` at `K:a45f06`; `K:a931ed` installs `set_frame_ctrl_imp` there. It rejects a software state ≤2, then calls `isp_fw_send_frame_ctrl` on an eligible path. The wrapper passes `0x02050001`, a `0xa50`-byte payload and the previously resolved ring to `isp_send_fw_cmd_ex` at `K:a902bc`. By comparison, `isp_fw_set_send_buffer` submits `0x02060001` with a 48-byte descriptor. A buffer send can represent output or temporary working storage. Its existence does not identify an input plane. |
| 3. Move a command and receive the reply | `isp_send_fw_cmd_ex` checks ring space, arranges the payload and calls `insert_isp_fw_cmd` at `K:a88a7a`. Its failure path frees pending command resources. `ispm_sw_init` calls `isp_register_isr`; the vendor AMDGPU graphics-service functions have call relocations to `amdgpu_irq_add_id` (module `.text+0x15873e`) and `amdgpu_irq_get` (`+0x158796`). Registration uses AMD interrupt client 5 and the four source IDs `4,6,8,10` (kernel ELF `+0x1cd6c00`). `isp_ip_pwr_on` starts response threads. `isp_isr` signals an event at `K:a77dc4`; the worker waits with a timeout and invokes `isp_fw_resp_func` at `K:a77b65`. `isp_get_f2h_resp` checks a 64-byte record by summing the first 63 bytes modulo 256 and comparing the final byte at `K:a8a1ec–a8a1f6`. Jupiter interrupt routing remains **UNKNOWN**. [AMD interrupt client definition](https://github.com/torvalds/linux/blob/v5.4/drivers/gpu/drm/amd/include/soc15_ih_clientid.h#L36) |
| 4. Distinguish completion from command acceptance | `isp_fw_resp_func` dispatches `0x10001` to `isp_fw_resp_cmd_done` for command bookkeeping. It dispatches `0x10002` (`RESP_ID_FRAME_DONE`) to `isp_fw_resp_frame_ctrl_done` at `K:a84ac9`. That handler issues callback event `0x10` at `K:a84409`. `on_isp_registered` passes `func_lib_callback` at `K:a471f9` via registration slot `+0x100`, whose implementation stores the callback at `K:a94a7d`. On event `0x10`, `func_lib_callback` removes a pending buffer and calls `vb2_buffer_done` at `K:a45af4`. `0x10003` (`RESP_ID_FRAME_INFO`) has a different handler and callback event. `0x10004` (`RESP_ID_ERROR`) bypasses the frame-done path in this dispatcher. |
| 5. Return the buffer | The HAL’s `DQ_drvRes` issues the matching dequeue operation at `H:8dadd`. `_ioctl_default` calls `deq_result` at `K:a44619`; its paths use `vb2_dqbuf`, `send_shutter` and `send_buf_rst`. `send_buf_rst` checks buffer status and copies information back to userspace at `K:a3e632`. Separate pending-list, bad-metadata and invalid-stream checks can stop a frame from completing. |

## Android reprocessing is a separate path

**CONFIRMED.** At `H:5933f`, `amdCamera3Hwi::processCaptureRequest` branches on the Android `input_buffer` pointer after stream validation. A non-null path reaches `sendToReprocess` at `H:59599`. `processReprocessRequest` calls through the reprocess callback object at `H:78521`; its vtable relocation at `0xd06f0` resolves to `processReprocFrame`. The callback can feed a scaler, compressor and container, matching the three objects created by `amdCamera3Reprocess` at `H:77ba9–77be1`. `amdCamera3Scaler::process` calls `NV12ToI420` and `I420Scale` (`H:86c2b`, `H:86ceb`). The compressor has software and hardware JPEG branches (`H:88439`, `H:884e2`). These are concrete host-side reprocessing edges. Their presence supplies no link to an ISP3 raw input. [Android 10 capture request ABI](https://android.googlesource.com/platform/hardware/libhardware/+/9c3fea3ac451821a47437eb53790d0297143c45a/include/hardware/camera3.h#2389)

**CONFIRMED.** In both shipped capability XMLs, every tuple in `ANDROID_SCALER_AVAILABLE_STREAM_CONFIGURATIONS` has output direction; each lists `YCbCr_420_888` with minimum advertised size 640 × 480. Both declare zero input streams. The HAL sanity checker has code for an input stream and rejects a combined input/bidirectional count ≥2 at `H:740a4`. This is compatible with compiled reprocessing support that the products do not advertise. The smallest usable sensorless input dimensions, pixel packing, supported transform and independently verified output on ISP3 remain **UNKNOWN**.
