# ISP3 command and response records in Mero build 9601

**CONFIRMED.** The host uses 64-byte records on four command rings and four response rings. The command ID identifies an operation. Its requested stream and the physical ring that carries it can differ. In particular, a frame-info command from a **valid** requested stream is routed over global command ring 0. The ordinary memory camera's reset value 4 fails the ring check *before* that routing decision. This explains why finding a global frame-info receiver does not close the memory-camera path. [Camera mapping and producer search](isp3-frame-evidence.md)

All `K:` offsets below are relative to virtual address `0xffffffff81000000` in the original Magic Leap 2 OS 1.12.1 build 9601 x86 `boot/vmlinux`, SHA-256 `f8891033b1f3b9cf9f25ef76d914173f1d43ff9a75df6764982207f0bd84f642`. `F:` is a file offset in `vendor/lib/firmware/amdgpu/mero_isp.bin`, SHA-256 `2a8c6ae8b24d2613cf5f862ded9240100b2c3ffedcb4d5b2193fc0eb8e656fb0`. The observations are from static inspection. No runtime command packet or matched memory-frame response from a headset was available. [Archive provenance](../evidence/artifacts.md) · [Member inventory](../evidence/host-index.tsv)

## The host-to-firmware record

Offsets are bytes from the start of a single little-endian record. `isp_send_fw_cmd_ex` clears the entire record at `K:a882e2–a88333`. It passes the record's address to the function named **`insert_isp_fw_cmd`** in the shipped symbols at `K:a88a6f–a88a7a`.

| Offset | Interpretation on build 9601 | Evidence |
|---|---|---|
| `0x00–03` | **CONFIRMED** 32-bit command sequence number. The host starts the context counter at 1, uses its current value and increments it for the next command. | `ispm_sw_init` at `K:a7864d`, `get_nxt_cmd_seq_num` at `K:a8715e–a8716d`, inlined update at `K:a8839a–a883a4`, record store at `K:a88685`. |
| `0x04–07` | **CONFIRMED** 32-bit command ID. | `isp_send_fw_cmd_ex` stores it at `K:a88340`. Insertion dispatches on the same word at `K:a87551`. |
| `0x08–37` | **CONFIRMED** 48 parameter bytes. A direct call copies its command-specific payload here, up to 48 bytes. An indirect call stores the package descriptor described below. | Direct-size check at `K:a881e0–a881e9`, direct copy at `K:a8836e–a88385`, indirect construction at `K:a885bc–a885e3`. The caller selects the form. No general direct/indirect bit or inline length was identified in this envelope. |
| `0x38–39` | **CONFIRMED** 16-bit stream tag. Requested rings 1, 2 and 3 encode tags 0, 1 and 2. Requested ring 0 encodes `0xffff`. | The decrement, unsigned comparison, conditional move and 16-bit store are at `K:a88344–a88354`. | `0x3a–3e`, `0x3f` | The five bytes before the checksum are zero-initialized on this path. Their independent semantics are **UNKNOWN**. **CONFIRMED** final byte = sum of bytes 0 through 62, modulo 256. | `K:a882eb` clears the trailer. `K:a88685–a886a2` stores the sequence, sums the bytes and writes the final byte. |

**CONFIRMED indirect package.** The observed Mero encoder places the low and high 32-bit halves of the package's MC address at record offsets `0x08` and `0x0c`, a 32-bit byte count at `0x10`, and the low eight bits of the separate package-byte sum at `0x14`. The code calls `isp_split_addr64` at `K:a88427` or `K:a885de`, stores the size at `K:a8842c` or `K:a885e3`, and stores a one-byte sum at `K:a8866c` or `K:a88cb7` on the pooled-package branch. `isp_send_fw_cmd_by_dma_buf` independently reads an existing allocation and builds the same overlay (`K:a893f9–a89414`, `K:a89510–a89531`). This is the location of the **command's parameter package**. An input or output pixel address would have to be established inside the appropriate command-specific payload. [Buffer address domains](isp3-buffer-dependencies.md)

The related AMD ISP4 source names similar sequence, ID, parameter and stream fields, but declares a 32-bit final checksum and a compile-time larger-record variant. The Mero read/write sites above establish the byte at `0x3f` for this build. The ISP4 header alone would give an incorrect Mero checksum location. [AMD ISP4 public types, pinned source](https://github.com/amd/Linux_ISP_Kernel/blob/5b316a3d3ba4f799cb333c823b87f0793ea139a2/drivers/media/platform/amd/isp4/isp_module/src/isp_fw_if/param_types_pub.h#L38-L109)

The routing is **CONFIRMED** by three branches in `insert_isp_fw_cmd`. The unsigned bound rejects a requested index ≥4 at `K:a874b3–a874f6`. The selected physical ring starts at zero at `K:a87555–a87562`. The frame-info and send-buffer comparisons at `K:a875ab–a875b7` retain zero. The ordinary branch copies the requested index at `K:a875bf–a875d9`. `K:a87615–a87623` then obtains space in the **selected** ring. The other globally routed ID ranges in this decision tree are `0x01010001–02`, `0x01020003–07`, `0x01030001–04`, `0x01040001–02` and `0x01060001–04` (inclusive, with the leading digits shared). The embedded stream tag has already been constructed from the **requested** index. Firmware's normal response-ring selection for every possible global-routed command remains **UNKNOWN**.

**CONFIRMED additional firmware gate.** In the wrapped Xtensa image, the dispatch scheduler's nonblocking-channel branch accepts both global and stream-control operations. With the image body at VA `0x60000000` (file `+0x200`), VAs `0x60093fdb–0x60093fe1` load class `0x02000000` and mask `0xff000000`. At `0x600942fc–0x6009430d` it masks the record's command ID and sends class 2, which includes `SEND_FRAME_INFO`, to the stream-control branch. At `0x600943fb–0x600943fe` it reads record offset `0x38` (stack+72, record at stack+16) and takes the normal branch for unsigned tags below 3. The other branch selects a diagnostic identifying an out-of-range stream and takes an error path at `0x60094401–0x60094432`. This explains the host's two-level routing. A physical ring-0 record can carry a valid stream tag, while the tag `0xffff` produced for a *requested* ring 0 fails the firmware stream-control gate. Passing the tag check would still leave the input producer, configured stream and completed frame to establish. [Memory-camera reset, alternate sensor type and command search](isp3-frame-evidence.md)

**CONFIRMED partial frame-info layout.** A separate `SEND_FRAME_INFO` branch in `isp_send_fw_cmd_ex` examines the caller's parameter data before logging. It joins two dwords at parameter offsets `0x77c/0x780`, sums three dwords at `0x784/0x790/0x79c`, and reports the resulting address, address-plus-length and length (`K:a887c3–a887c8`, `K:a888cf–a888f7`, `K:a88947–a88980`). These reads cover at least **`0x7a0` bytes** starting at the parameter pointer. A complete object matching the inspected fields exceeds the 48-byte inline limit and therefore requires a separate parameter package in the ordinary host transport. **STRONG EVIDENCE** for an embedded three-plane buffer layout beginning at `0x774`, given the spacing and observed `SEND_BUFFER` layout above. This host diagnostic establishes a lower bound. The wrapped firmware supplies the exact `0x1278` size via its command-table entry at `F:17038`, handler VA `0x6008d718`, comparison at `0x6008d736` and length literal at `F:86120`. The companion RAM file instead has dispatch record `+0xb7d8`, target VA `0x60092e9c`, comparison at `0x60092ebd` and `0x1230` literal at file `+0x83438`. The ordinary host producer of the full structure and a frame trace remain **UNKNOWN**. ## Insertion and receipt

1. **Allocate rings. CONFIRMED.** `isp_fw_buf_get_cmd_base` supplies four slices of `0x1900` bytes (100 records each) from offset `0xa00000` of its work arena at `K:a92205–a9223f`. `isp_fw_buf_get_resp_base` supplies four `0x3200`-byte slices (200 records each) from arena offset `0xa06400` at `K:a922a5–a922df`. Both helpers select the per-ring offset from that ring's index and can return CPU and MC views of the same storage. `isp_init_fw_ring_buf` zeroes cursors and programs base and length through graphics-services callbacks at `K:a8a9cb–a8aabb`. These are offsets in Mero's allocated work arena. Jupiter's PSP reservation has a different provenance. [Boot and trusted-memory evidence](isp3-firmware-and-smu.md)
2. **Reserve a command slot. CONFIRMED.** Host code is the producer of the command write cursor. Firmware supplies the consumer's read cursor. `no_fw_cmd_ringbuf_slot` calculates advancement by 64 at `K:a872aa–a872c8`, including wrap. In the normal slot-aligned case, the next write position reaching the read position means full. One command slot is kept free, so at most 99 records can be queued in one physical ring. `isp_send_fw_cmd_ex` checks space on the requested ring under a mutex and, if full, sleeps up to ten times with a 20 ms request before reporting `0x10` (`K:a88294–a882e0`, `K:a884e3–a884f0`). Insertion separately checks the selected physical ring at `K:a87618–a8762a` and can fail there.
3. **Publish the record. CONFIRMED.** The normal aligned copy moves four 16-byte chunks. The code also handles a copy split at the end of the ring. It executes `mfence` before the copy at `K:a8776e`, then `sfence`, advances the byte cursor by 64 with wrap, and publishes the new write position at `K:a87911–a8793a`. This last publication is the observed host notification. In `mero_isp.bin`, write-pointer interrupt names at `F:90ec` onwards and the ring-interrupt handler label at `F:96e0` supply **STRONG EVIDENCE** for firmware-side notification. A second independently issued doorbell was not found in the insertion routine. The optimized 16-byte copy does not specify pixel-plane alignment.
4. **Receive a response. CONFIRMED.** The host consumes the response read cursor and reads the firmware's write cursor. Equal cursors return `0x10` (empty), and an incomplete record takes an error branch (`K:a8a043–a8a054`, `K:a8a106–a8a10b`). `isp_get_f2h_resp` copies 64 bytes, including wrap when needed, publishes an advanced host read position at `K:a8a19c–a8a1b0`, and checks the modulo-256 sum at `K:a8a1b5–a8a1f6`. A bad record has already been consumed when the checksum error is reported. The response worker passes 5 ms to its per-ring event wait, checks for stop, and calls the response dispatcher under a mutex (`K:a77b10–a77b65`). It also checks on timeout. An IRQ alone cannot identify a completed frame. [Frame and callback path](isp3-frame-evidence.md#one-complete-output-buffer-path-in-the-shipped-camera-stack)

**Cursor validation for saved snapshots.** The normal zero-initialized command writer publishes positions that are multiples of 64 in `[0, ring_length)` (`K:a8a9cb–a8aa2e`, `K:a87911–a8793a`). This is a defensible input convention for a read-only decoder. The actual input checks at `K:a876b5–a876b8` and `K:a87709–a8770c` initially admit values equal to the length and reject larger values. The response reader makes the same initial distinction (`K:a89f81–a89f84`, `K:a89fda–a89fdc`) and subsequently checks the contiguous or wrapping distance. Treat a captured one-past-end cursor as noncanonical. A blanket equivalence to zero was not established for every branch.

**Independent firmware-side check.** The wrapped firmware's `SendCmdDoneResp` builder (VA `0x60076a30`) prepares a 48-byte body and checks for more than 36 reply bytes at `0x60076a7e–0x60076a91`. The rejected-length branch stores halfwords **1** at body+8 and **27** at body+10 (`0x60076a9c–0x60076aa4`). The diagnostic at `F:ff88` identifies the oversized reply. The ordinary branch stores caller-supplied halfwords in the same positions at `0x60076b24–0x60076b27`. The outer builder puts ID `0x10001` at record+4 and a distinct response counter at +0 (`0x60076abf–0x60076ad5`), supplies the prepared body and destination record+8, then stores a byte at +63 at `0x60076af3`. The associated checksum routine at `0x60108470–0x601084da` sums unsigned bytes and retains the low eight bits. A second builder at `0x60076b50` uses the same layout. This gives host/firmware agreement about the error-detail slot for a specific condition. AMD's related public table calls value 27 a package-size error. [Cross-version comparator](https://github.com/amd/Linux_ISP_Kernel/blob/5b316a3d3ba4f799cb333c823b87f0793ea139a2/drivers/media/platform/amd/isp4/isp_module/src/isp_fw_if/cmd_resp_pub.h#L368-L373)

**CONFIRMED host lifetime.** The sender's host-only pending record is 80 bytes. It records the sequence, command ID, requested ring, pooled package or separate GPU allocation, and optional completion event and response pointers (`K:a886d4–a88752`). For indirect commands up to the pool-slot size `0x5400`, the normal sender reserves a work-buffer slot. Larger packages use a separate GPU allocation (`K:a86e89`, `K:a883d9–a8842c`, `K:a884f5–a8850b`). Insertion failure unwinds the pending record and owned package at `K:a88aa6–a88ae5`. On command-done the handler returns pooled storage, frees a separately owned allocation and releases the host pending record at `K:a83f9d–a83fd2`. The DMA-buffer wrapper accepts an existing allocation. Its name alone does not establish that the payload describes input pixels.

The synchronous wrapper waits for its caller-supplied timeout at `K:a88dfe–a88e15`. Its timeout branch (`0x10`) looks up the pending pair and releases owned command resources at `K:a88e2e–a88e7a`. A command acknowledgement concerns the command package. Pixel-buffer ownership extends to the frame completion and dequeue on the ordinary output path. A timeout cannot certify that an engine has stopped using an image buffer. [DMA and buffer-lifetime evidence](isp3-buffer-dependencies.md)

## Reproduce on extracted files

Use the hash-identified kernel and firmware above. These commands disassemble ordinary files and inspect firmware text. The ring routing, packet construction and command-done correlation can be checked with these bounds. The two firmware commands use GNU Binutils 2.44 built for `xtensa-elf`. Some configuration-specific bundle operations display as `excw`; the identified size/ID tests, loads, stores and branch targets support the field conclusions. [Extraction guide](../reports/reproduction.md)

```sh
llvm-objdump -d --no-show-raw-insn -j .text -j .init.text vmlinux | rg -i '\b0x(8664|fc64|17264|1e864)\b'
llvm-objdump -d --start-address=0xffffffff81a874b0 --stop-address=0xffffffff81a8762c vmlinux
llvm-objdump -d --start-address=0xffffffff81a882e2 --stop-address=0xffffffff81a8838a vmlinux
llvm-objdump -d --start-address=0xffffffff81a8866c --stop-address=0xffffffff81a886b0 vmlinux
llvm-objdump -d --start-address=0xffffffff81a83ecd --stop-address=0xffffffff81a83f78 vmlinux
xtensa-elf-objdump -D -b binary -m xtensa --adjust-vma=0x5ffffe00 --start-address=0x60076a30 --stop-address=0x60076b50 mero_isp.bin
xtensa-elf-objdump -D -b binary -m xtensa --adjust-vma=0x5ffffe00 --start-address=0x600943b2 --stop-address=0x60094438 mero_isp.bin
strings -tx mero_isp.bin | rg 'IhRingBufferIntrHandler|StreamMgrCmdSendFrameInfo|IspPipeMgrSendHostFrameInfo'
```

The [file-only ring decoder](../scripts/decode_isp3_ring.py) reads a saved slot or a complete ring with separately recorded normalized read/write byte pointers. For example, `python3 scripts/decode_isp3_ring.py command saved-slot.bin --ring 0 --payload saved-package.bin` reports the original tag, expected physical ring, size and checksum. For a full saved response ring, supply both `--read-pointer` and `--write-pointer`. On a single direct SEND_BUFFER, `--owned-range BASE BYTES` checks nonempty plane extents against an independently known allocation in the same address domain. A passing numeric check says nothing about mapping or cache coherence. The decoder never resolves a recorded address. [Synthetic fixtures and tests](../tests/test_isp3_ring.py)
