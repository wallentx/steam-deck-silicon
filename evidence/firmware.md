# CVIP firmware in ML2 OS 1.12.1, build 9601

The build contains two classes of CVIP firmware that can be investigated separately. Five boot components carry an AMD firmware header. The CVIP read-only filesystem exposes four substantive DSP program images, four small profiling tables, an AArch64 vision runtime, job maps and model parameters. The [artifact inventory](cvip-side.tsv) records sizes, SHA-256 digests, file types, architecture evidence and next inspections for all 226 regular files in that filesystem, the single regular file in the writable filesystem, and the outer artifacts examined here. Paths beginning with `package/` refer to members below the top-level archive directory. Paths beginning with `cvip_ro/` or `cvip_rw/` refer to files inside the named filesystem.

All five boot wrappers contain `$PS1` at offset 0x10, little-endian 1 at 0x18 and 0x30, ASCII `R016` at 0x60, the exact file size at 0x6c and a type byte at 0x7c. AMD defines the 0x18 and 0x30 fields as encryption and signature selectors in a documented 256-byte header. Coreboot's header parser agrees on the signature, size and type offsets. The fields are CONFIRMED and the evidence for encryption and signing of these payloads is STRONG. Neither the certificate chain nor on-device authentication was verified. A full byte scan of each wrapped file found no FDT, ELF, lzop, ARM64 Image or newc CPIO magic. Header load-address fields read zero. The inner target entry points and addresses remain UNKNOWN. [AMD publication 58453, appendix B.1](https://www.amd.com/content/dam/amd/en/documents/epyc-technical-docs/user-guides/58453.pdf) · [coreboot header at 1922d75](https://chromium.googlesource.com/chromiumos/third_party/coreboot/+/1922d75ca04136d6691a14b3e143cfd03cfa998f/util/amdfwtool/amdfwtool.h) · [coreboot PSP integration guide](https://doc.coreboot.org/soc/amd/psp_integration.html)

The vendor debug helper lists `c5_0`, `c5_1` and `q6_0` through `q6_5` at line 134. It selects the Xtensa core at lines 115-128 and treats 0xc4000000-0xc5ffffff as Q6 code and 0xc6000000-0xc7ffffff as C5 code at lines 136-146. The four program images begin with words in these family ranges. The four accompanying profiling files contain little-endian address words and zeros, with five words per C5 table and 15 per Q6 table. The job-map addresses fall in the corresponding DSP ranges. These are DSP address-space values. An x86 physical mapping or a hardware reset vector cannot be derived from them. The four substantive files carry raw program images. Cadence independently documents Vision Q6 for embedded vision and Vision C5 for neural-network workloads. The combination strongly supports the 6xQ6 + 2xC5 assignment. The exact Xtensa configuration, optional instruction extensions and core revision remain UNKNOWN. ## Compute evidence and limits

The shipping hand-tracking package refers to `ht_detection_net_weights.bin` at ELF file offset 0x32dd8 and `ht_keypoint_net2_weights.bin` at 0x32e80 in `libhand_tracking_pkg-cvip-arm-hw.so`. The files have 5,005,824 and 15,945,216 bytes, respectively. The 1,428,992-byte Q6 eye-network weights are referenced by `libeye_pkg-cvip-arm-hw.so` at 0x31c58. The presence of weights larger than the published on-chip SRAM rules out using the advertised SRAM size alone as the maximum model file size. The C5 program explicitly checks free local DRAM0 and DRAM1 at offsets 0x979 and 0x9ad and reports insufficient network memory at 0xa3d. The runtime's placement strategy and peak live working set remain UNKNOWN. [Full file and digest inventory](cvip-side.tsv)

The Q6 program names an 8-bit color conversion. The AArch64 hand-tracking library exposes `KeypointNetOutput::GetDequantizedHand` at VA 0x42080. These observations support U8 image processing and quantized hand-network outputs. They do not specify the width of the C5 multiply-accumulate datapath, every tensor's format, the measured memory bandwidth or achievable throughput. The RO image also ships five ZIP-format model resources with a .pt extension. Their presence does not establish a public PyTorch loader on the DSP. No serialized model or proprietary executable was run. [DSP, ARM library and model provenance](cvip-side.tsv)

The named jobs and separate code images establish vendor programmability and deployment for CV inference, tracking, feature extraction and preprocessing. General tensor dispatch, third-party graph compilation and LLM execution remain UNKNOWN. A practical port needs a matching DSP compiler and core configuration, a compatible task/transport ABI, shareable buffers with known cache rules, and an authorized hardware boot path. A controlled test would also need the workload shape and precision plus latency for submission, memory transfer and completion. This release supplies existing jobs and evidence for an ARM task runtime. It does not supply those measurements. [Firmware-loading evidence](../analysis/firmware-loading.md)

## Reproduction

The [CVIP-side inventory script](../scripts/cvip-side.py) verifies the three sparse images against build 9601, uses simg2img, walks ext4 through read-only debugfs calls, and copies regular file contents into a fresh destination without executable permission. The parser checks each inode's recorded size. A second extraction via debugfs rdump independently agreed on all 226 SHA-256 digests for CVIP RO. The version-specific inventory can be regenerated from the investigation directory with Python 3.11+ and Arch's Android sparse tools and e2fsprogs.

```bash
python scripts/cvip-side.py work/package work/cvip-side-recheck > work/side-recheck.tsv
cmp evidence/cvip-side.tsv work/side-recheck.tsv
```
