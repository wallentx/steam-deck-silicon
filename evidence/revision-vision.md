# CVIP programs and calibration across ML2 releases

Magic Leap lists OS 1.2.1 as the earliest compatible release for T2 MedTech devices and 1.3.1 for T2 Enterprise devices. We compared four actual public firmware packages. The 1.2.0 and 1.2.1 images carry byte-identical DSP programs, task maps, model resources and CV engine configuration. Three ARM libraries change executable code, and all three concern calibration. This narrows where a change supporting new hardware could reside. The comparison does not identify the part that changed on a T2 device. ### 1.2.0 to 1.2.1

**CONFIRMED.** All 220 CVIP RO paths exist in both releases. Exactly 179 files have identical bytes and 41 differ. The matching set covers all 13 substantive C5/Q6 programs, six profile files, nine job maps, all ten model resources, and all 37 configuration files in the configuration class. The developer helper defines the same two C5 and six Q6 core names in both builds. The changed set contains two ARM executables, 38 ARM libraries and one peripheral image. Of the 40 ARM ELF files with changed whole-file hashes, 37 differ only in the contents of the build-ID and debuglink sections among their named, file-backed sections. This includes the CV engine orchestrator. [File hashes](revision-vision.tsv) · [Section hashes](revision-vision-elf.tsv) · [Job-map addresses](revision-vision-jobs.tsv)

The source for the table is the static comparison of corresponding ELF sections and llvm-objdump / addr2line results on both versions. Magic Leap's release notes independently identify changes to display calibration and handling of headsets without the Bend Camera. The intersection provides **STRONG EVIDENCE** for a calibration compatibility change. The documented feature can occur elsewhere as well. The three AArch64 code differences do not establish which firmware change enables T2 boot. **CONFIRMED.** The remaining changed file, orion/peq3b.ihex, is present under the same name in all four builds. Its ASCII records use a byte count, three address bytes, record type, data and a checksum. Every record in the four files sums to zero modulo 256. Comparing data records by address, the 1.2.1 file removes 208 populated bytes, adds no new addresses and changes 63,809 bytes at common addresses. This establishes a genuine peripheral payload change. The file provides no demonstrated link from PEQ3B to the T2 serial code or to the C5/Q6 cores. [Per-path hashes](revision-vision.tsv)

### 1.3.1 and 1.12.1

**CONFIRMED.** From 1.2.1 to 1.3.1, all 11 retained non-profile DSP images change. The separate C5 and Q6 clock binaries and their profiling companions disappear from this filesystem. Seven of the nine job maps change. The two matching files are the C5 eye-service and Q6 r2d-service maps. Across the combined Q6 job map, 25 typed symbols survive the update, all at new addresses. Nine of ten model files retain identical hashes. Only et_network_weights.bin changes. The helper continues to name two C5 and six Q6 cores. These observations show build-specific job addresses and workload changes at the Enterprise T2 compatibility floor. They do not identify a new execution core. [File and model hashes](revision-vision.tsv) · [Job-map values](revision-vision-jobs.tsv)

**CONFIRMED.** The 1.12.1 read-only image contains four substantive DSP binaries, comprising C5/Q6 service and combined application images. Every one differs from its 1.3.1 predecessor. The seven separate per-service program images and maps present in 1.3.1 are absent. The only two duplicate DSP-related .bin files between 1.3.1 and 1.12.1 are the combined application's small C5 and Q6 profiling tables. Six model resources remain byte-identical across all four releases, including ht_detection_net_weights.bin, ht_detection_nms_weights.bin and SuperPointNet.pt. File identity does not identify where each resource executes. [File hashes](revision-vision.tsv) · [Latest runtime and DSP evidence](firmware.md)

## Wrapped A55 boot components

Every release has the same five named boot wrappers, including ml-mero-cvip-mortable.dtb.hbin. All twenty headers contain the AMD magic at 0x10, encryption flag 1 at 0x18 and signing flag 1 at 0x30. The type IDs are stable for each filename. All five whole-file hashes change at every transition. From 1.2.0 to 1.2.1, the kernel, CBL, DTB and OEM file lengths stay identical, while the ramfs wrapper grows by 1,359,952 bytes. Across 1.2.1 to 1.3.1, CBL grows from 376,304 to 1,876,720 bytes. Ciphertext and header differences cannot establish plaintext changes to an equal-length payload. The inner DTB nodes, silicon stepping and early initialization changes remain **UNKNOWN**. The ramfs wrapper sets its compression flag to zero throughout the four builds despite the .lzo filename. ## Board attribution and reproducibility

The same Linux DSP debug helper appears in all four packages. Its line 134 names c5_0, c5_1, and q6_0 through q6_5. The three older releases contain identical deployment helpers; all four assign the CVIP DTB to a file named mortable. Bring-up code uses a PEQ hardware-revision prefix to choose device behavior and the read-only images carry an Orion payload named peq3b. Those names identify development/configuration conventions. The comparison found no mapping that assigns a DSP image, a change of core count, or an A55 silicon stepping to T0, T1 or T2. A manufacturer parts record or a serial-matched read-only inventory would be necessary to make that attribution. [Helper hashes](revision-vision.tsv) · [Magic Leap's model and serial classification](https://developer-docs.magicleap.cloud/docs/releases/releases-overview/#hardware-and-software-compatibility-matrix)

The analysis expanded each Android sparse cvip_ro.img.hbin with simg2img and read all ext4 regular files by inode using [the read-only extractor](../scripts/extract-ext4.py). File comparisons use SHA-256. The ELF comparison uses SHA-256 of the exact named section bytes; .text and .rodata are reported separately from .note.gnu.build-id. The job matrix keys each row by file and mangled symbol so that an address change is distinguishable from a signature change. All four packages were inspected statically. No physical device supplied a serial number or a running-state measurement.
