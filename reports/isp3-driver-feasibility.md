# Can a minimal driver process a memory-backed frame on the LCD Deck?

The [follow-on trace search](isp3-trace-attempt.md) tested the proposed offline experiment against the factory archive and public samples. It identified a picture-order field in the firmware scheduler but found no recorded input frame to replay.

**A working sensorless path has not been established, and the stock F7A0133 firmware supplies a concrete power-control blocker.** The ordinary AMDGPU-facing SMU table on Jupiter has empty entries for ISP power up/down and the two ISP clock minima. Mero populates all four. Both packaged firmwares encode interface version **3** as their version-query reply, even though the Mero **driver** expects 2. Matching Linux message names or matching interface numbers cannot fix the table difference. This is a static finding in the exact distributed capsules, supported by the Deck's matching live firmware version. It does not identify a fuse. [Firmware dispatch comparison](../analysis/isp3-smu-compatibility.md)

**The memory-input lead is now a real receiver with a missing producer.** Both ISP programs dispatch `SEND_FRAME_INFO` (`0x02050002`). The wrapped image requires **4,728** bytes of frame information; the RAM image requires **4,656**. A valid requested stream preserves its tag while this command travels on physical ring 0. Logical camera 3's reset mapping still fails before insertion, and requesting global stream 0 gives a tag that the wrapped stream-control dispatcher rejects. An ordinary physical camera provides a valid tag, but the audited software supplies no corresponding source-plane producer. The firmware enqueues and can dequeue frame information. No traced pixel transaction links that queue to an external input plane. Reading externally supplied pixels, processing them, and returning their result are separate, unverified edges. [Command ABI](../analysis/isp3-command-protocol.md) · [Memory-input evidence](../analysis/isp3-memory-input.md)

## Success criteria

| Question | Verdict |
|---|---|
| 1. Can ISP3 initialize without CVIP? | **CONFIRMED in Mero code** that registration and a stream-setup branch can avoid CVIP's buffer callbacks. **UNKNOWN** whether a cold start through readiness and a complete frame can succeed without the subsystem. **DISPROVEN** that all four stock Mero ISP power/clock requests have handlers on Jupiter's ordinary graphics mailbox. [Callbacks](../analysis/isp3-buffer-dependencies.md) · [SMU](../analysis/isp3-smu-compatibility.md) |
| 2–3. Is there a valid memory-input path to firmware? | **CONFIRMED** command decoding, package checks and queue handoff. **UNKNOWN** host construction of an owned source-plane descriptor, valid stream selection for that producer, and pixel ingestion. A broad ELF search and the ordinary capture positive control narrow the gap. [Memory input](../analysis/isp3-memory-input.md) |
| 4–5. What address is required, and can upstream provide it safely? | Mero's **output** path uses a pinned AMDGPU BO's graphics aperture address, carried as low/high 32-bit words with lengths. Neptune has a kernel-only GTT BO allocation path for supported ISP4 children. Jupiter ISP3's memory-input translation, address width, cache domain and fence contract remain **UNKNOWN**. A 64-bit field specifies representation, not accessible memory. [DMA feasibility matrix](../analysis/isp3-dma-portability.md) |
| 6–7. Will the firmware and SMU support Jupiter? | **UNKNOWN** PSP authentication, trusted-memory placement, CCPU reset and actual ISP execution. The images identify the same Xtensa LX7 configuration but differ on the frame-info ABI. Jupiter's packaged graphics-mailbox handler table is concrete evidence against using the stock Mero callbacks unchanged. [Firmware boot](../analysis/isp3-firmware-boot.md) · [SMU controls](../analysis/isp3-smu-compatibility.md) |
| 8. How would a host detect a successful frame? | Require a valid `FRAME_DONE` response, matching metadata and pending output buffer, successful queue state and verified output contents. An IH interrupt, ready flag or `CMD_DONE` alone does not establish a frame. [Frame lifecycle and sequence diagram](../analysis/isp3-ring-lifecycle.md) · [Interrupts and apertures](../analysis/isp3-interrupts.md) |
| 9–10. What blocks a proof, and what should be tested first? | The Mero input descriptor producer and pixel consumer, Jupiter's ISP-specific power/firmware path, and the ISP-visible buffer/interrupt contracts. The smallest discriminating experiment is offline and described below. |

## Minimum driver architecture

| Part | Minimum responsibility | Current status |
|---|---|---|
| **A. Offline-verifiable** | Parse saved command and response records, check checksums, separate requested stream tag from physical ring, validate snapshot bounds, correlate command acknowledgements, compare the exact firmware tables and package sizes. | Implemented as file-only tools. Synthetic fixtures exercise valid and invalid checksums, wraparound, slot ownership, both frame-info sizes, same-domain plane bounds, and command-versus-frame completion. [Ring decoder](../scripts/decode_isp3_ring.py) · [Tests](../tests/test_isp3_ring.py) · [Build verifier](../scripts/inspect-isp3-build.py) · [SMU image comparison](../scripts/compare_isp3_smu.py) |
| **B. Hardware-dependent** | An AMDGPU-owned ISP3 IP block would own initialization state, signed firmware staging, ready checks, a small bounded pool of kernel-owned buffers, command/response ownership, IH registration and teardown. Any eventual test interface would select a fixed test image and return completion plus a checked result. No caller would supply device addresses. | Architectural proposal only. Initialization must unwind in reverse ownership order. Timeout returns an error; late DMA must be quiesced before memory is freed or reused. The ordinary capture sequence supplies a control for this design. [Lifecycle](../analysis/isp3-ring-lifecycle.md) |
| **C. Unknown or blocked** | Identify a supported Jupiter board/firmware contract for power and reset, an accepted image and address domain, and an actual producer and consumer for an input plane. Confirm IRQ delivery and a frame-specific synchronization contract. | A loadable skeleton would leave these gates unresolved. The read-only work used no driver load, SMU command, hardware DMA or firmware execution. [Live hardware boundary](../evidence/deck-live/isp3-boot-check.md) |

**Smallest safe next experiment.** Take an already recorded, known-working **Mero memory-input** frame and decode the command slot and its separately saved package using the correct image size. Follow one source-plane identity through the valid stream tag, firmware input-consumer queue, pixel read and matching completed output. A buffer address in a debug print or a successful metadata acknowledgement is insufficient. The same acceptance criteria can be tested against the corresponding licensed R64 source if a trace is unavailable. A successful correlation would establish a Mero software path; Jupiter's graphics-mailbox finding would still apply.

From the repository root, run `python3 -B -m unittest discover -s tests -v`. The decoder accepts a saved 64-byte slot or a saved entire ring with normalized byte cursors, and an optional separate package file. It never follows addresses in the input. The corpus scanner reproduced two incidental executable-section matches in 2,623 hash-verified ELF members. The [earlier feasibility report](isp3-feasibility.md) preserves the prior ISP3 and secondary findings. This investigation concentrated on the new protocol, firmware and DMA evidence.
